1. TRANSACTION FLOW — Atomic Transaction End-to-End
================================================================================

File: AtomicTransactionProcessor.java -> BeforePostLedgerProcessor.java
      -> (async) AfterPostLedgerProcessor.java

The atomic transaction is a single-shot reserve+transfer. Example: user A
sends 100 USDT to user B. This produces:

  TransactionLines:
    { walletRef=A, assetCode=USDT, operationType=Debit,  amount=100 }
    { walletRef=B, assetCode=USDT, operationType=Credit, amount=100 }

2. IDEMPOTENCY FLOW
================================================================================

File: IdempPrecheckProcessor.java

  idempAndValidatePrecheck(requestInfo)
  |
  +-- 1. ValidateHelper.requestPrecheck()
  |     Checks: serviceId, businessType, transactionType not UNKNOWN
  |     Each line: operationType valid, amount > 0
  |     FAIL before touching Redis -> no cleanup needed
  |
  +-- 2. claimIdempCacheIfAbsent()
  |     Key: idemp_k:WALLET:post_transaction:{idempotencyKey}
  |     Value: "P:{stableHash}:{token}"
  |     TTL: pendingTtl + random(jitterMs)
  |
  |     SET NX -> [success] -> return success(null) = "claimed, proceed"
  |
  |     SET NX -> [fail] -> GET key -> parse IdempValue
  |       [parse fails] -> forceDeleteIdemp() -> return null (fall to DB)
  |       [hash mismatch] -> FAIL REQUEST_HASH_CONFLICT
  |       [status=PENDING] -> FAIL REQUEST_IN_PROCESSING
  |       [status=ACCEPTED] -> return success(txnId) = "already done"
  |
  +-- 3. DB FALLBACK
  |     selectByIdempotencyKey(serviceId, idempotencyKey)
  |     [found] -> markIdempDone() -> return success(txnId)
  |     [not found] -> return success(null) = "new request, proceed"

  Key difference from ledger-service:
    - Idempotency key is caller-provided (idempotencyKey field), not referenceId
    - Scope is "post_transaction" (Constant.SCOPE)
    - Hash includes more fields: referenceId, serviceId, idempKey, businessType,
      transactionType, requestName, and all sorted line fields


3. BALANCE SNAPSHOT UPDATE — SQL-Level Atomic Guards
================================================================================

File: BalanceSnapshotRepository.java

All balance mutations use SQL-level atomic guards to prevent negative values.
This is the primary concurrency control for balances.

  reserve(id, walletId, assetId, amount):
    UPDATE balance_snapshots
    SET available = available - {amount},
        reserved = reserved + {amount}
    WHERE id = {id}
      AND wallet_id = {walletId}
      AND asset_id = {assetId}
      AND wallet_status = 'OPEN'
      AND available >= {amount}          -- GUARD: prevents overdraft
    Evidence: BalanceSnapshotRepository.java lines 46-58

  release(id, walletId, assetId, amount):
    UPDATE balance_snapshots
    SET available = available + {amount},
        reserved = reserved - {amount}
    WHERE id = {id}
      AND wallet_id = {walletId}
      AND asset_id = {assetId}
      AND wallet_status = 'OPEN'
      AND reserved >= {amount}           -- GUARD: prevents negative reserved
    Evidence: lines 61-74

  transferOut(id, walletId, assetId, amount):
    UPDATE balance_snapshots
    SET reserved = reserved - {amount}
    WHERE id = {id}
      AND wallet_id = {walletId}
      AND asset_id = {assetId}
      AND wallet_status = 'OPEN'
      AND reserved >= {amount}           -- GUARD: prevents negative reserved
    Evidence: lines 76-88

  transferIn(id, walletId, assetId, amount):
    UPDATE balance_snapshots
    SET available = available + {amount}
    WHERE id = {id}
      AND wallet_id = {walletId}
      AND asset_id = {assetId}
      AND wallet_status = 'OPEN'
    -- NO guard needed: available always increases
    Evidence: lines 90-101

  affected_rows == 0 means the guard failed (insufficient funds or wallet
  not OPEN). The caller treats this as BALANCE_SNAPSHOT_UPDATE_FAILED.


4. RESERVATION LOCKING AND UPDATE
================================================================================

File: UpdateReservationProcessor.java

  updateReservations(reservations, function):
  |
  +-- 1. Collect reservation IDs
  +-- 2. SELECT ... IN (ids) FOR UPDATE  (pessimistic lock by PK)
  |     Evidence: WalletReservationRepository.selectInIdForUpdate, line 46-49
  |     The wrapper uses .last("for update")
  +-- 3. For each locked reservation:
  |     a. BeanUtils.copyProperties(reservation, copy)  -- snapshot "old" state
  |     b. function.apply(reservation)                   -- mutate in place
  |     c. if (reservation != copy):                     -- only update if changed
  |        updateWithOptimisticLock(reservation, copy)
  |        WHERE id=? AND status=old.status AND remaining=old.remaining
  |          AND pendingSettle=old.pendingSettle AND consumed=old.consumed
  |          AND released=old.released
  |        Evidence: WalletReservationRepository.java lines 73-81
  |     d. [affected=0] -> FAIL RESERVATION_UPDATE_FAILED
  |
  Belt-and-suspenders:
    - FOR UPDATE prevents concurrent reads from seeing stale data
    - Optimistic lock (WHERE old-values) catches any logic bugs where
      the in-memory state diverges from what was locked
    - Both BeforePostLedgerProcessor and AfterPostLedgerProcessor use
      this same pattern with different mutation functions


5. TWO-STEP TRANSACTION FLOW
================================================================================

Phase 1: Reserve
────────────────
  ReserveTransactionProcessor.reserve()
    - Validates all lines are OperationTypePb_Reserve
    - IdempPrecheck
    - BeforePostLedgerProcessor.beforePostingLedger(requestInfo, needPostLedger=FALSE)
      Because needPostLedger=false:
        - txn status set to COMPLETED immediately (line 72)
        - No outbox created
        - No Kafka publish
        - Balance: available -= amount, reserved += amount
        - Reservation created: remaining=amount, everything else=0

  Returns: txnId + list of ReservationInfoPb (reservation_ref, wallet_ref,
           asset_code, amount)
  Caller saves reservation_ref for phase 2.

Phase 2: Apply (Earmark or Release)
────────────────────────────────────
  ApplyReservationTransactionProcessor.apply()
    - IdempPrecheck
    - BeforePostLedgerProcessor.beforePostingLedger(requestInfo, needPostLedger=TRUE)

    For OperationTypePb_Earmark lines:
      - Loads existing reservation by reservation_ref
      - Creates CONSUME + TRANSFER_OUT actions
      - CONSUME: reservation.remaining -= N, reservation.pendingSettle += N
      - TRANSFER_OUT: will post to ledger
      - Outbox created for ledger posting

    For OperationTypePb_Release lines:
      - Loads existing reservation by reservation_ref
      - Creates RELEASE action
      - RELEASE: reservation.remaining -= N, reservation.released += N
      - Balance: reserved -= N, available += N (funds returned)

    After ledger reply: AfterPostLedgerProcessor settles the earmarked funds
      (pendingSettle -> consumed, reserved -= amount)


6. WALLET CREATION — Multi-Step With Crash Recovery
================================================================================

File: CreateWalletProcessor.java

  createWallet(req)
  |
  +-- 1. VALIDATE: serviceId, ownerType
  |
  +-- 2. CHECK EXISTING: walletMapper.selectByReferenceId(serviceId, refId)
  |     [exists AND initiated (OPEN/FROZEN/CLOSE)] -> return "already created"
  |     [exists AND INIT] -> skip to step 4 (resume from crash)
  |     [null] -> step 3
  |
  +-- 3. CREATE WALLET: insertIgnore(wallet, status=INIT)
  |     [affected=0] -> FAIL WALLET_DUPLICATED
  |       (another thread beat us; they'll finish creation)
  |
  +-- 4. CREATE LEDGER ACCOUNT: gRPC to AccountService
  |     Creates liability account with credit normal side
  |     referenceId = walletId (1:1 mapping)
  |     Category = Liability, NormalSide = Credit
  |     This means wallet balances are tracked as liabilities
  |     to users (exchange owes users their funds).
  |     Evidence: lines 102-116
  |     [error] -> return fail (wallet stays in INIT state)
  |
  +-- 5. ENABLE WALLET (DB Transaction):
  |     ┌────────────────────────────────────────────────────┐
  |     │ UPDATE wallet SET status=OPEN WHERE status=INIT    │
  |     │   [affected=0] -> FAIL (concurrent thread already  │
  |     │   enabled it)                                      │
  |     │                                                    │
  |     │ INSERT IGNORE wallet_account_mapping               │
  |     │   (walletId -> walletId)                           │
  |     │                                                    │
  |     │ INSERT IGNORE balance_snapshot                     │
  |     │   (available=0, reserved=0)                        │
  |     └────────────────────────────────────────────────────┘
  |
  +-- 6. RETURN success

  Crash recovery design:
    - INIT state is a "halfway" marker
    - If crash after step 3 but before step 5:
      Next call sees wallet in INIT -> resumes from step 4
    - If crash after step 4 but before step 5:
      ledger createAccount is idempotent (insertIgnore)
      -> safe to call again -> then continue to step 5
    - INIT->OPEN transition is CAS (WHERE status=INIT)
      -> only one thread can succeed


7. ERROR HANDLING
================================================================================

  Same Result<T> monad pattern as ledger-service.

  Wallet ErrorCode enum has 50+ codes (ErrorCode.java):
    - Internal errors (0-9): SUCCESS, UNKNOWN, SERVER, NULL_RESULT, DB, SERIALIZE
    - Validation (100): INVALID_REQUEST_PARAMETER
    - Idempotency (200-201): REQUEST_HASH_CONFLICT, REQUEST_IN_PROCESSING
    - Entity-specific (1000+): per entity NOT_FOUND, DUPLICATED, UPDATE_FAILED,
      MISMATCH, NOT_SATISFIED, NOT_AVAILABLE
    - Cross-service (10000+): CREATE_ACCOUNT_FAILED, POST_TRANSACTION_FAILED

  gRPC service layer: try/catch(Exception) around every processor call.
  Uncaught exceptions -> SERVER_ERROR proto reply.

  Idemp key release: every error path in BeforePostLedgerProcessor calls
  releaseIdempBeforeReturnError() before returning. Uses the same Lua
  compare-and-delete script as ledger-service.
  Evidence: BeforePostLedgerProcessor.java lines 167-174

  Kafka consumer: throws RetriableException on AfterPostLedger failure,
  which triggers Spring Kafka's error handler for retry.
  Evidence: DefaultListener.java lines 60-62
