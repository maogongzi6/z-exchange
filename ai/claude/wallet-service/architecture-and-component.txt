================================================================================
 WALLET SERVICE — ARCHITECTURE & KEY COMPONENTS
================================================================================


1. SYSTEM OVERVIEW
================================================================================

The wallet service is the business-facing layer of the exchange platform.
It manages user and system wallets — balances, reservations, and fund
transfers — while delegating the actual double-entry bookkeeping to the
downstream ledger service.

It implements a two-phase financial transaction model:
  - Atomic transactions: reserve + transfer in one shot (synchronous start,
    async ledger posting, async completion)
  - Two-step transactions: reserve first, then apply (earmark/release) later

Tech stack:
  - Spring Boot + grpc-spring-boot-starter (net.devh)
  - MyBatis-Plus (ORM)
  - Redis (Redisson) for idempotency (via common-util's IdempRedisClient)
  - Kafka for async communication with ledger-service
  - Protobuf for gRPC + Kafka serialization
  - Depends on common-util for: outbox, idempotency, DB helpers, Result monad

  wallet_enum.proto — domain enums:
    OwnerTypePb: Unknown, System, User

    TransactionTypePb: Unknown, Atomic
    TransactionStatusPb: Unknown, Pending, Completed, Closed

    OperationTypePb: Unknown, Reserve, Earmark, Release, Debit, Credit

  wallet_transaction.proto — request/reply messages:
    AtomicTransactionRequestPb: {reference_id, initiator, idempotency_key, business_type, lines[]}
    ReserveTransactionRequestPb: same shape

2.2 Service Layer
────────────────────────────
  WalletServiceImpl (@GrpcService)
    Thin gRPC handler. Delegates to processors. Catches all uncaught exceptions
    and returns SERVER_ERROR. Four endpoints:
      createWallet -> CreateWalletProcessor
      atomicTransaction -> AtomicTransactionProcessor
      reserveTransaction -> ReserveTransactionProcessor
      applyReserveTransaction -> ApplyReservationTransactionProcessor

2.3 Processor Layer — Transaction Processing Pipeline
──────────────────────────────────────────────────────
  The transaction processors share a common pipeline via step processors:

  Entry-point processors (one per RPC):
    AtomicTransactionProcessor.executeAtomic()
    ReserveTransactionProcessor.reserve()
    ApplyReservationTransactionProcessor.apply()

  All three follow the same pattern:
    1. Generate token
    2. Build RequestInfo (unified model for all transaction types)
    3. IdempPrecheckProcessor.idempAndValidatePrecheck()
    4. BeforePostLedgerProcessor.beforePostingLedger(requestInfo, needPostLedger)
    5. Return result

  Step processors (shared logic):
    IdempPrecheckProcessor:
      - Validates request (enums, amounts, business type)
      - Redis idempotency claim (SET NX via IdempRedisClient)
      - DB fallback check (selectByIdempotencyKey)
      Same three-tier pattern as ledger-service

    BeforePostLedgerProcessor:
      - Creates WalletTransaction
      - Loads BalanceSnapshots by wallet refs
      - Loads existing WalletReservations (for earmark/release ops)
      - Creates WalletActions from each TransactionLinePb
      - Creates new WalletReservations (for reserve/debit ops)
      - Validates actions against snapshots and reservations
      - Creates outbox for ledger posting (if needed)
      - Single DB transaction: update reservations, update snapshots,
        insert reservations, insert txn, insert actions, insert outbox
      - Mark idempotency DONE
      - Best-effort publish outbox to Kafka

    AfterPostLedgerProcessor:
      - Triggered by Kafka reply from ledger-service
      - Loads WalletTransaction by txnId
      - If already finalized: return immediately (idempotent)
      - Loads TRANSFER_IN/TRANSFER_OUT/CONSUME actions
      - Loads snapshots and reservations for affected wallets
      - Single DB transaction: settle reservations (consumed),
        update snapshots (transferOut/transferIn), update txn -> COMPLETED
      - Reservation auto-finishes when total == consumed + released

    UpdateReservationProcessor:
      - SELECT FOR UPDATE on reservation rows (locked by PK order)
      - Applies a function to each reservation
      - Writes back with optimistic lock (checks all amount fields match)

2.4 Wallet Creation
────────────────────────────
  CreateWalletProcessor:
    1. Validate request (serviceId, ownerType)
    2. Check if wallet already exists (by serviceId + referenceId)
       [exists and initiated] -> return success ("already created")
       [not exists] -> INSERT IGNORE wallet (status=INIT)
    3. gRPC call to ledger-service: AccountService.createAccount()
       Creates a liability account with credit normal side
       referenceId = walletId (1:1 wallet-to-account mapping)
    4. DB transaction: update wallet INIT->OPEN, insert WalletAccountMapping,
       insert BalanceSnapshot (available=0, reserved=0)

2.5 Kafka Integration
────────────────────────────
  Producer (DefaultPublisher):
    Publishes outbox events to Kafka topic WALLET_POST
    (wallet.ledger.command.posting)
    Synchronous send with 3s timeout

  Consumer (DefaultListener):
    Listens on LEDGER_REPLY topic (ledger.wallet.reply.posting)
    Handles POST_LEDGER_REPLY events:
      Parses PostTransactionReplyPb from envelope payload
      Calls AfterPostLedgerProcessor.afterPostLedger(referenceId)
      referenceId in the ledger reply = walletTxn.txnId
      (because wallet sets PostTransactionRequestPb.referenceId = txnId)

  Outbox (OutboxDispatcher):
    @Scheduled cron job delegates to OutboxRetryHandler.retry()
    Same pattern as ledger-service outbox


3. DATA FLOW
================================================================================

3.1 Create Wallet
─────────────────

  Caller --gRPC--> WalletServiceImpl.createWallet
                      |
                CreateWalletProcessor
                      |
       1. Validate enums
       2. Check wallet exists in DB
       3. INSERT IGNORE wallet (status=INIT)
       4. gRPC -> Ledger AccountService.createAccount
          (Liability account, credit normal side, refId=walletId)
       5. DB Transaction:
          - UPDATE wallet status INIT -> OPEN
          - INSERT wallet_account_mapping (walletId -> walletId)
          - INSERT balance_snapshot (available=0, reserved=0)
       6. Return success

3.2 Atomic Transaction (e.g. Transfer)
──────────────────────────────────────

  Caller --gRPC--> WalletServiceImpl.atomicTransaction
                      |
                AtomicTransactionProcessor
                      |
       1. Generate token
       2. Build RequestInfo (type=ATOMIC)
       3. IdempPrecheckProcessor:
          - Validate request
          - Redis idemp claim
          - DB fallback if needed
       4. BeforePostLedgerProcessor (needPostLedger=true):
          |
          | For each TransactionLinePb:
          |   OperationTypePb_Debit -> creates actions:
          |     RESERVE (available -> reserved in snapshot)
          |     CONSUME (reserved -> pendingSettle in reservation)
          |     TRANSFER_OUT (will post to ledger)
          |   OperationTypePb_Credit -> creates action:
          |     TRANSFER_IN (will post to ledger)
          |
          | DB Transaction:
          |   - Update snapshots (reserve amounts)
          |   - INSERT reservations (with pendingSettle = amount)
          |   - INSERT wallet_transaction (status=PENDING)
          |   - INSERT wallet_actions
          |   - INSERT outbox (POST_LEDGER command)
          |
          | Mark idemp DONE
          | Best-effort publish outbox -> Kafka(WALLET_POST)
          |
       5. Return (txnId, status=PENDING)

  --- Async phase ---

  Outbox -> Kafka(wallet.ledger.command.posting) -> Ledger Service
    Ledger processes double-entry posting
    Ledger replies -> Kafka(ledger.wallet.reply.posting)

  DefaultListener.onMessage
       |
       | Parse PostTransactionReplyPb
       | AfterPostLedgerProcessor.afterPostLedger(txnId)
       |
       | DB Transaction:
       |   - Settle reservations: pendingSettle -> consumed
       |   - Update snapshots: reserved -= transferOut, available += transferIn
       |   - Update wallet_transaction status PENDING -> COMPLETED
       |
       | ACK Kafka

3.3 Reserve Transaction (Two-Step, Phase 1)
───────────────────────────────────────────

  Caller --gRPC--> WalletServiceImpl.reserveTransaction
                      |
                ReserveTransactionProcessor
                      |
       1. Validate all lines are OperationTypePb_Reserve
       2. Idemp check
       3. BeforePostLedgerProcessor (needPostLedger=false):
          |
          | For each line:
          |   RESERVE action: snapshot.available -= amount, snapshot.reserved += amount
          |   New reservation: remaining = amount
          |
          | DB Transaction: same as atomic but NO outbox, status=COMPLETED
          |
       4. Return (txnId, reservationInfos[])

  No Kafka involved. Funds are held in the "reserved" bucket.

3.4 Apply Reservation (Two-Step, Phase 2)
─────────────────────────────────────────

  Caller --gRPC--> WalletServiceImpl.applyReserveTransaction
                      |
                ApplyReservationTransactionProcessor
                      |
       1. Idemp check
       2. BeforePostLedgerProcessor (needPostLedger=true):
          |
          | For each line (OperationTypePb_Earmark or OperationTypePb_Release):
          |   Earmark -> CONSUME + TRANSFER_OUT (reserved -> ledger)
          |   Release -> RELEASE (reserved -> available)
          |
          | DB Transaction + outbox for TRANSFER_OUT/TRANSFER_IN lines
          |
       3. Async ledger posting (same as atomic)
       4. AfterPostLedgerProcessor completes the txn

3.5 System Interaction Diagram
──────────────────────────────

  External Caller
       |
       | gRPC
       v
  Wallet Service
       |
       +-- gRPC --> Ledger Service (AccountService.createAccount)
       |            (only during wallet creation)
       |
       +-- Kafka(wallet.ledger.command.posting) --> Ledger Service
       |   (PostTransactionRequestPb via outbox)
       |
       +-- Kafka(ledger.wallet.reply.posting) <-- Ledger Service
           (PostTransactionReplyPb)
           |
           +-- AfterPostLedgerProcessor (finalize wallet txn)


4. KEY COMPONENTS
================================================================================

4.1 BeforePostLedgerProcessor — The Core Orchestrator
──────────────────────────────────────────────────────
  File: processor/transaction/step/BeforePostLedgerProcessor.java

  The most critical class. Orchestrates the entire pre-ledger phase of
  every transaction type. Single method: beforePostingLedger(requestInfo, needPostLedger)

  Dependencies:
    - TransactionTemplate (programmatic DB transactions)
    - IdempRedisClient (idemp finalization)
    - BalanceSnapshotRepository, WalletReservationRepository,
      WalletTransactionRepository, WalletActionRepository,
      WalletAccountMappingRepository, OutboxRepository
    - DefaultPublisher (Kafka)
    - UpdateReservationProcessor (reservation locking + update)
    - CustomCacheConfig.Idemp (TTL config)

  Key behaviors:
    - When needPostLedger=false (reserve only): sets txn status to COMPLETED
      immediately, no outbox created
    - When needPostLedger=true: sets txn status to PENDING, creates outbox,
      attempts immediate Kafka publish after DB commit
    - Balance updates use SQL-level atomic operations:
      "available = available - amount WHERE available >= amount"
      This prevents negative balances without application-level locks
    - Releases idemp key on ANY error before returning

  Operation type -> action mapping (ObjectBuilder.createActionsFromLine):
    OperationTypePb_Reserve -> [RESERVE]
    OperationTypePb_Earmark -> [CONSUME, TRANSFER_OUT]
    OperationTypePb_Release -> [RELEASE]
    OperationTypePb_Debit   -> [RESERVE, CONSUME, TRANSFER_OUT]
    OperationTypePb_Credit  -> [TRANSFER_IN]

  Debit is a compound operation: reserve + consume + transfer_out in one shot.
  This is the atomic equivalent of the two-step reserve-then-earmark flow.

4.2 AfterPostLedgerProcessor — Async Completion
────────────────────────────────────────────────
  File: processor/transaction/step/AfterPostLedgerProcessor.java

  Triggered by Kafka consumer when ledger replies.
  Completes the transaction by settling reservations and updating balances.

  Key behaviors:
    - Idempotent: checks hasFinalized() before processing
    - Only processes TRANSFER_IN, TRANSFER_OUT, CONSUME actions
    - For CONSUME: pendingSettle -> consumed (reservation settlement)
    - For TRANSFER_OUT: reserved -= amount (balance deduction)
    - For TRANSFER_IN: available += amount (balance credit)
    - Updates txn status to COMPLETED
    - Reservation auto-finishes: when total == consumed + released,
      status -> FINISHED, outcome is inferred (CONSUMED/RELEASED/PARTIAL)

4.3 UpdateReservationProcessor — Pessimistic Locking
─────────────────────────────────────────────────────
  File: processor/transaction/step/UpdateReservationProcessor.java

  Used by both BeforePostLedgerProcessor and AfterPostLedgerProcessor.
  Applies a function to a list of reservations with proper locking.

  Pattern:
    1. SELECT ... FOR UPDATE on reservation rows (by PK order)
    2. BeanUtils.copyProperties to capture "old" state
    3. Apply the provided function (which mutates the reservation)
    4. Compare new vs old — if changed, UPDATE with optimistic lock:
       WHERE id=? AND status=old.status AND remaining=old.remaining
         AND pendingSettle=old.pendingSettle AND consumed=old.consumed
         AND released=old.released

  This is belt-and-suspenders: pessimistic lock (FOR UPDATE) prevents
  concurrent access, and the optimistic lock (WHERE old values match)
  provides defense-in-depth.

4.4 IdempPrecheckProcessor — Three-Tier Idempotency
────────────────────────────────────────────────────
  File: processor/transaction/step/IdempPrecheckProcessor.java

  Same pattern as ledger-service's idempotency:
    Layer 1: Redis SET NX (key = idemp_k:WALLET:post_transaction:{idempKey})
    Layer 2: DB query by (serviceId, idempotencyKey) composite
    Layer 3: DB INSERT IGNORE on wallet_transactions

  Key = idempotencyKey (caller-provided), NOT referenceId.
  This allows callers to retry with the same idempotency key.
  Hash = Murmur3-128 of all request fields (sorted lines, excluding token).

4.5 CreateWalletProcessor — Wallet Provisioning
────────────────────────────────────────────────
  File: processor/CreateWalletProcessor.java

  Multi-step creation with crash recovery:
    1. INSERT IGNORE wallet (status=INIT)
       If dup: re-read from DB. If already OPEN: return success.
       If still INIT: continue from step 2 (resume).
    2. gRPC call to ledger AccountService.createAccount
       Creates a liability account with credit normal side.
       Account referenceId = walletId (1:1 mapping).
    3. DB transaction: INIT->OPEN + insert mapping + insert snapshot
       The status transition INIT->OPEN is a compare-and-swap
       (WHERE wallet_status = INIT). Only one thread can succeed.

  The wallet-to-account mapping is currently 1:1 (comment in
  WalletAccountMapping.java line 18: "now the ref id is wallet_id,
  because wallet to account is 1:1 mapping").

5.2 Reservation Lifecycle
─────────────────────────

  A reservation tracks the flow of funds through these buckets:

                         total
                           |
                    ┌──────┴──────┐
                    |             |
                remaining    (settled)
                    |       /    |    \
                    |  consumed  |  released
                    |       pendingSettle
                    |
  On creation:    total = remaining (reserve) or pendingSettle (debit)

  State transitions:
    Reserve:   remaining = total, consumed=0, pendingSettle=0, released=0
    Consume:   remaining -= N, pendingSettle += N
    Settle:    pendingSettle -= N, consumed += N (after ledger confirms)
    Release:   remaining -= N, released += N

  Terminal: when remaining=0 and pendingSettle=0 (isTotallySettled)
    Outcome: CONSUMED (all consumed), RELEASED (all released), PARTIAL (mix)

5.3 Balance Bucket Model
────────────────────────

  Each wallet has two buckets tracked in balance_snapshots:

    ┌──────────────────────────────────────────────────┐
    │                Wallet Balance                     │
    │                                                  │
    │  ┌──────────────┐    ┌──────────────┐            │
    │  │   AVAILABLE   │    │   RESERVED   │            │
    │  │              │    │              │            │
    │  │  Spendable   │    │  Held by     │            │
    │  │  balance     │    │  reservations│            │
    │  └──────────────┘    └──────────────┘            │
    │                                                  │
    │  reserve:   available -= N, reserved += N        │
    │  release:   available += N, reserved -= N        │
    │  transferOut: reserved -= N (leaves the wallet)  │
    │  transferIn:  available += N (enters the wallet) │
    └──────────────────────────────────────────────────┘

      - event_type = "POST_LEDGER_REPLY"
      - reply.referenceId = walletTxn.txnId (used to look up the txn)

7. RELATIONSHIP TO LEDGER SERVICE
================================================================================

  The wallet and ledger services form a coordinated pair:

  ┌──────────────────────┐          ┌──────────────────────┐
  │    Wallet Service     │          │    Ledger Service     │
  │                      │          │                      │
  │  User-facing API     │          │  Bookkeeping engine  │
  │  Balance management  │          │  Double-entry records │
  │  Reservations        │          │  Account management  │
  │  Two-phase txns      │          │  Entry validation    │
  │                      │          │                      │
  │  wallet_transactions │          │  ledger_transactions │
  │  wallet_actions      │          │  ledger_entries      │
  │  wallet_reservations │          │  accounts            │
  │  balance_snapshots   │          │  assets              │
  └──────────┬───────────┘          └──────────┬───────────┘
             │                                 │
             │  1. createWallet triggers       │
             │     createAccount (gRPC)        │
             │                                 │
             │  2. Transaction posting flows:  │
             │     Wallet --Kafka--> Ledger    │
             │     Ledger --Kafka--> Wallet    │
             │                                 │
             │  3. Wallet txnId = Ledger       │
             │     referenceId (correlation)   │
             └─────────────────────────────────┘

  Separation of concerns:
    - Wallet owns: balances, reservations, business rules, user-facing API
    - Ledger owns: double-entry invariant (debit==credit), audit trail
    - Wallet decides WHAT moves; Ledger records HOW it moves

  Transaction correlation:
    - Wallet txn.txnId is used as PostTransactionRequestPb.referenceId
    - Ledger stores this as ledger_transactions.reference_id
    - Ledger reply includes the same referenceId for correlation
    - Wallet consumer uses it to find the WalletTransaction
