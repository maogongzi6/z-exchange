2. CONCURRENCY & CONSISTENCY
================================================================================

2.1 Idempotency Under Concurrent Identical Requests
────────────────────────────────────────────────────

  Case: Two requests with same referenceId and same body arrive simultaneously

    Request A                           Request B
    ---------                           ---------
    SET NX idemp key -> succeeds        SET NX idemp key -> FAILS
      (P:hash:tokenA)                     |
      |                                   GET key -> PENDING/tokenA
      |                                   -> FAIL REQUEST_IN_PROCESSING
      v
    DB INSERT -> succeeds
    markIdempDone(tokenA, txnId)
                                        Request B (retries later)
                                          GET key -> ACCEPTED/txnId
                                          -> return txnId (cached)

  Case: Same referenceId, DIFFERENT body (hash mismatch)

    Request A (hash=X)                  Request B (hash=Y)
    SET NX -> succeeds                  SET NX -> fails
      |                                   GET -> hash X != Y
      |                                   -> FAIL REQUEST_HASH_CONFLICT

2.2 Redis Key TTL Expiry Mid-Flight
────────────────────────────────────

    T0   A: SET NX -> success (P:hash:tokenA, TTL=pendingTtl)
    T1   A: starts processing (slow account resolution)
    T30  Redis: key TTL expires
    T31  B: SET NX -> success (P:hash:tokenB)
    T32  A: INSERT IGNORE -> affected=1 (first to DB)
    T33  B: INSERT IGNORE -> affected=0 (dup) -> ROLLBACK
    T34  A: markIdempDone(tokenA) -> SET "A:hash:tokenA:txnId" (unconditional)
    T35  B: releaseIdempIfOwned(tokenB)
           Lua: GET -> "A:hash:tokenA:txnId" != "P:hash:tokenB" -> no delete

  Result: DB backstop prevents double-write. B does wasted work but no corruption.
  The unconditional SET in markIdempDone (line 59 of IdempRedisClient) overwrites
  B's PENDING claim, but the final state is correct (ACCEPTED with A's txnId).

2.5 Transaction Boundary Design
───────────────────────────────

  postTransaction DB write:
    TransactionTemplate + PROPAGATION_REQUIRED
    Scope: INSERT txn + batch INSERT entries (atomic)
    Rollback: on Result.isFailed() via DbTransactionHelper (line 17:
      transactionStatus.setRollbackOnly())

  Redis operations: OUTSIDE the DB transaction
    - Idempotency claim: before DB transaction
    - Cache cleanup + idemp finalize: after DB commit
    Rationale: Redis is not part of the ACID boundary. Redis failure
    is tolerable because DB is the source of truth, and the system
    self-heals via DB fallback queries.

  Outbox claim (OutboxRetryHandler):
    Separate transaction per page
    SELECT FOR UPDATE SKIP LOCKED -> batch claim -> COMMIT
    Then publish (outside tx) -> finalize (new update per batch)

2.6 SELECT FOR UPDATE SKIP LOCKED — Outbox Concurrency
───────────────────────────────────────────────────────

  OutboxRepository.selectForClaimSkipLock (lines 57-65):
    WHERE outbox_status = PENDING
      AND attempt_count < maxRetries
      AND next_attempt_at <= now
      AND id >= lastId
    ORDER BY id ASC
    LIMIT pageLimit
    FOR UPDATE SKIP LOCKED

  SKIP LOCKED is critical for horizontal scaling:
  - Multiple cron instances can run concurrently
  - Each skips rows already locked by the other
  - No contention, no deadlocks, no duplicate delivery attempts

4. CACHE LOGIC
================================================================================

4.1 Wire Format
───────────────

  Simple cache (ValueCodec):
    Encode: "{marker}:{content}"
    Markers: S=string, J=json, T=tombstone, N=negative
    Examples:
      "S:abc123"                -> STRING, value="abc123"
      "J:{\"txnId\":\"x\"}"    -> JSON, deserialized object
      "T:"                     -> TOMBSTONE, value=null
      "N:"                     -> NEGATIVE, value=null

  Versioned cache (VersionCodec):
    Encode: "{version}|{marker}:{content}"
    Examples:
      "5|J:{\"txnId\":\"x\"}"  -> version=5, JSON object
      "6|T:"                   -> version=6, TOMBSTONE

  Version prefix enables the Lua CAS script to extract and compare
  without deserializing the JSON body.
  Evidence: VersionCodec.java line 35, ValueCodec.java line 51

4.2 CacheValueInfo and Hit Semantics
─────────────────────────────────────

  CacheValueInfo<T>: { value, cacheType, version }

  ifCacheHit() logic (CacheValueInfo.java lines 35-39):
    null info       -> false (cache miss)
    TOMBSTONE       -> false (treated as miss, forces DB read)
    NEGATIVE        -> true  (valid hit indicating "does not exist")
    value != null   -> true  (valid data hit)

  getValidValue() (lines 19-27):
    TOMBSTONE/NEGATIVE -> null
    Otherwise          -> value

  This distinction is critical:
    - TOMBSTONE = "I invalidated this; re-read from DB" (write-side signal)
    - NEGATIVE = "This key doesn't exist in DB" (read-side protection)

5. RESULT AND ERROR HANDLING
================================================================================

5.1 The Result<T> Monad
────────────────────────

  File: common-util/.../utils/result/Result.java

  Structure:
    boolean success         -> fast check
    T value                 -> payload on success (nullable even on success)
    PbMappableErrorCode errorCode -> ALWAYS present (SUCCESS when ok)
    String errorDetail      -> human-readable context

  Two-class error code hierarchy:

    PbMappableErrorCode (interface)
      toProto() -> ErrorCodePb
      getMessage() -> String
            |
    +-------+--------+
    |                |
  CommonErrorCode  ErrorCode
  (common-util)    (ledger-service)
  codes: negative  codes: positive
  -------          -------
  SUCCESS(0)       SUCCESS(0)
  LUA(-100)        UNKNOWN(1), INTERNAL(2), SERVER(3)
  IDEMP_KEY(-1000) INVALID_PARAM(100)
  IDEMP_VAL(-1001) HASH_CONFLICT(200), IN_PROCESSING(201)
  PARSE_CACHE(-1100) LEDGER_DUPLICATED(1000), NOT_FOUND(1001)
                   ACCOUNT_NOT_FOUND(1100), ASSET_NOT_FOUND(1200)
                   OUTBOX_DUPLICATED(2000)

  Cross-module boundary enforcement:
    ledger-service Results.getErrorCode(result) (Results.java lines 37-43):
      if (result.errorCode.getClass() != ErrorCode.class)
        throw ClassCastException
    This is an intentional fail-fast: infrastructure errors (CommonErrorCode)
    must NOT be surfaced as business errors. If a CommonErrorCode leaks into
    a business-layer Result path, it crashes immediately rather than silently
    producing a wrong proto error code.

5.2 Two Results Classes
───────────────────────

  common-util Results (com.exchange.common.utils.result.Results):
    success(value)  -> Result(true, value, CommonErrorCode.SUCCESS, null)
    fail(error, detail) -> Result(false, null, error, detail)
    Used by: cache, idemp, outbox infrastructure

  ledger-service Results (com.exchange.app.ledger.result.Results):
    success(value)  -> Result(true, value, ErrorCode.SUCCESS, null)
    fail(ErrorCode, detail) -> Result(false, null, errorCode, detail)
    fail(Result<?>) -> propagates error code + detail from another Result
    getErrorCode(result) -> casts PbMappableErrorCode to ErrorCode with type check
    Used by: processors, services

  The same Result<T> class is shared, but factory methods attach different
  error code enums depending on the layer.

5.3 Error Propagation Flow
──────────────────────────

  Infrastructure (common-util)          Business (ledger-service)         gRPC boundary
  ─────────────────────────             ────────────────────────         ──────────────

  Redis/Cache error
    -> Result.fail(CommonErrorCode)
    -> logged, NOT propagated           Processor catches via
       (cache errors never block         result.isFailed() checks
        the main flow)                   |
                                         +-- Business validation error
                                         |     Results.fail(ErrorCode.INVALID_...)
                                         |     Propagated to caller
                                         |
                                         +-- DB error
                                         |     Result from DbTransactionHelper
                                         |     Auto-rollback on isFailed()
                                         |
                                         +-- Uncaught exception
                                               Caught in ServiceImpl try/catch
                                               -> PbErrorBuilder.build(SERVER_ERROR)
                                               -> ErrorPb in gRPC reply

  Key principle: cache/Redis errors are LOGGED but NEVER BLOCK the main flow.
  Every cache operation follows this pattern:

    Result<CacheValueInfo<T>> cacheResult = cache.get(id);
    if (!cacheResult.success) {
        log.error(...);  // observe, don't fail
        if (Result.is(cacheResult, CommonErrorCode.PARSE_CACHE_ERROR)) {
            cache.delete(key);  // self-recover
        }
    } else if (CacheValueInfo.ifCacheHit(cacheInfo)) {
        return cacheInfo.value;  // fast path
    }
    // fallthrough to DB (cache failure = transparent degradation)

5.5 Exception vs Result Boundaries
───────────────────────────────────

  Layer                   Error Mechanism             Rationale
  ─────                   ───────────────             ─────────
  Processor logic         Result<T> exclusively       Explicit, composable, no stack unwinding
  DB transactions         Result<T> inside            isFailed() triggers setRollbackOnly()
