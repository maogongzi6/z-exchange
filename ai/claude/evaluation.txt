================================================================================
 Z-EXCHANGE PROJECT — PRINCIPAL ENGINEER EVALUATION
================================================================================

 Evaluator perspective: Principal backend engineer
 Focus: System design, engineering judgment, trade-offs
 Scope: common-util, ledger-service, wallet-service
 Assumption: All flagged P0/P1 bugs treated as fixed


================================================================================
 MODULE 1: common-util
================================================================================

1. PROBLEM DECOMPOSITION                                              7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - Clean separation of cross-cutting concerns into a reusable library
    - Each sub-package (redis.idemp, redis.cache, outbox, db, utils) has
      a focused responsibility with minimal coupling between them
    - The cache framework is decomposed into layers: codec -> support ->
      client -> strategy -> abstract. Each layer has a single job
    - Result<T> and PbMappableErrorCode live here, establishing the
      error contract for the entire system

  Weak:
    - The outbox package includes both schema (Outbox entity) and runtime
      behavior (OutboxRetryHandler) in the same module. The retry handler
      depends on IPublisher, which couples common-util to service-level
      publishing logic. This means any service using the outbox must
      provide an IPublisher implementation and wire it into the shared
      OutboxRetryHandler bean — workable but slightly tangled
    - DbTransactionHelper lives in common-util but mutates a shared
      TransactionTemplate singleton (propagation setter). This is a
      design-level leak: infrastructure helpers should not impose
      statefulness on callers

  Improvement:
    DbTransactionHelper should accept a PlatformTransactionManager
    (immutable) rather than a TransactionTemplate (mutable singleton),
    and create TransactionTemplate internally per call. This removes
    the shared-state footgun at the API design level.


2. DOMAIN MODELING                                                    7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The cache type system (STRING, JSON, TOMBSTONE, NEGATIVE) with
      single-char markers is a well-modeled domain. CacheValueInfo's
      ifCacheHit() correctly distinguishes "actively cached null"
      (NEGATIVE) from "invalidated, go to DB" (TOMBSTONE) — this is
      a subtle but important distinction that many cache designs miss
    - IdempValue with its state machine (PENDING -> ACCEPTED) and the
      wire format "{status}:{hash}:{token}[:{content}]" captures the
      full idempotency lifecycle in a single Redis value
    - TtlStrategy as a value object encapsulating (base_ttl + jitter)
      is a clean domain concept

  Weak:
    - The PbMappableErrorCode interface ties the error model to protobuf
      at the common-util level. If a service needed non-gRPC error
      mapping (e.g. REST), this abstraction wouldn't work. The coupling
      is acceptable for this system but limits reuse
    - CommonErrorCode uses negative codes (-100, -1000) while service
      ErrorCodes use positive codes. The sign convention works as a
      namespace separator but is implicit — a developer could easily
      create a collision without realizing it

  Improvement:
    The error code hierarchy would be cleaner if PbMappableErrorCode
    were split: a generic ErrorCode interface (code + message) in
    common-util, with a separate ProtoMappable mixin interface that
    service-level enums implement. This decouples the infrastructure
    layer from protobuf.


3. ARCHITECTURE QUALITY                                               8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The cache framework's strategy pattern (VersionCacheAsideAbstract
      vs StableCacheAbstract) is the right abstraction for the problem.
      Services extend an abstract class, override getCacheKey() and
      getClazz(), and get a complete cache-aside or stable-cache
      implementation. This is genuinely well-designed
    - The Lua scripts (set-if-absent-or-newer, release-idemp-if-owned)
      are the correct solution for their respective atomicity problems.
      The version-comparison script extracting the version prefix from
      the wire format without full deserialization is clever and efficient
    - The outbox pattern with SELECT FOR UPDATE SKIP LOCKED is the
      industry-standard approach and is implemented correctly

  Weak:
    - The cache framework has many layers (6+ classes in the inheritance
      chain for a versioned cache read). The layering is logical but
      creates a steep learning curve for debugging. A simpler composition
      approach (decorators or functional composition) might achieve
      the same with fewer classes

  Improvement:
    Consider flattening the cache hierarchy by one level — merge
    ReadRedisSupport into SimpleRedisSupport/VersionedRedisSupport
    since ReadRedisSupport is only ever used as a base class. This
    reduces indirection without losing the abstraction.


4. CORRECTNESS BY DESIGN                                              7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The Lua CAS script (set-if-absent-or-newer) structurally prevents
      stale cache overwrites. This is correctness by design — the
      invariant (newer version always wins) is enforced atomically
      at the Redis level, not by application logic
    - CacheContentValidator.validateContent enforces that TOMBSTONE/NEGATIVE
      values must have empty content, and STRING/JSON must have non-empty
      content. This prevents malformed cache entries at encode time
    - DbBaseRepository.insertIgnore catches DuplicateKeyException and
      returns 0 instead of throwing — this makes idempotent writes the
      default behavior for all repositories

  Weak:
    - The release-idemp-if-owned Lua script checks value equality for
      ownership, but markIdempDone does a plain SET without any
      ownership check. The two operations have inconsistent safety
      levels — one is guarded, the other is not. The design should
      either guard both or explicitly document why the asymmetry is safe
    - Result<T> carries errorCode as a PbMappableErrorCode (interface),
      but service-level Results.getErrorCode() does a runtime class cast.
      The type system doesn't prevent mixing CommonErrorCode and
      service ErrorCode — the cast is a runtime assertion, not a
      compile-time guarantee

  Improvement:
    Make Result<T> generic on its error code type: Result<T, E extends
    PbMappableErrorCode>. This would catch cross-module error code
    mixing at compile time rather than runtime. The tradeoff is more
    verbose signatures, but for a financial system, compile-time
    correctness is worth the verbosity.


5. CONSISTENCY AND CONCURRENCY DESIGN                                 8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The idempotency system is a textbook three-tier design:
      Redis fast-path -> DB unique key -> DB fallback query.
      Each tier compensates for the failure modes of the one above
    - The Lua scripts provide true atomicity for the critical
      compare-and-swap operations (version check + SET, value check + DEL)
    - The outbox retry uses SELECT FOR UPDATE SKIP LOCKED, which is
      the correct primitive for contention-free work claiming across
      multiple instances
    - The versioned cache uses the DB @Version as the cache version,
      creating a natural total order for cache writes

  Weak:
    - The negative cache (StableCacheAbstract) uses plain SET without
      any concurrency guard. The design protects versioned data with
      Lua CAS but leaves stable data unguarded. The asymmetry is
      partially justified (stable data is immutable) but the negative
      cache IS mutable (it gets deleted after inserts) and should
      have been designed with the same care
    - No circuit breaker for Redis. The cache-first pattern means every
      request touches Redis. A Redis failure mode could cascade into
      DB overload. The design handles Redis errors gracefully (fallback
      to DB) but doesn't address the latency cost of failed connections

  Improvement:
    The negative cache should use SET NX (setIfAbsent) rather than
    plain SET. Alternatively, elevate the negative cache to the
    versioned strategy with a monotonic counter. This closes the
    race condition at the design level rather than relying on
    short TTLs as a mitigation.


6. RELIABILITY AND RECOVERY DESIGN                                    7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - Cache errors never block the main flow — this is a design
      principle consistently applied across every cache read path.
      Self-recovery (delete on parse error) is automatic
    - The outbox pattern provides at-least-once delivery guarantee.
      Combined with idempotent consumers, this achieves effective
      exactly-once semantics
    - The idempotency system self-heals: if Redis key expires, the
      DB fallback re-populates Redis on the next request

  Weak:
    - The OutboxRetryHandler has no execution time limit (TODO comment
      at line 33 acknowledges this). A large backlog could hold the
      cron thread for an unbounded duration
    - There's no explicit dead-letter or alerting mechanism in the
      outbox. Messages that exhaust max retries simply stop being
      picked up — no signal to operators

  Improvement:
    Add an explicit terminal state to the outbox (e.g. DEAD_LETTERED)
    that gets set when attempt_count >= maxRetries. A monitoring hook
    on this state enables alerting. This is a design-level addition,
    not a code fix.


7. SCALABILITY AND PERFORMANCE THINKING                               6/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - TTL jitter (TtlStrategy.afterJitter) prevents cache stampede —
      this shows awareness of thundering herd problems
    - The versioned cache Lua script avoids unnecessary deserialization
      by extracting the version from the wire format prefix
    - The outbox uses cursor-based pagination (lastId) instead of
      OFFSET, which is the correct approach for large tables

  Weak:
    - The outbox retry is single-threaded and sequential per instance.
      No parallel publish, no async IO. This is a throughput ceiling
      for outbox-heavy workloads
    - No batch support in the cache framework. Every cache get/set is
      a single Redis round-trip. For the wallet's "load snapshots for
      N wallets" pattern, this means N Redis calls where a MGET would
      be 1

  Improvement:
    Add MGET/MSET support to the cache clients. The cache framework
    already has the codec layer to handle per-key encoding/decoding;
    adding a batch API is a natural extension that significantly
    reduces Redis round-trips for multi-key lookups.


8. SIMPLICITY VS OVER-ENGINEERING                                     6/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The EnumMapper utility is simple and eliminates repetitive
      enum-conversion code across services. Good ROI
    - insertIgnore() in DbBaseRepository is a one-line pattern that
      eliminates a class of bugs (duplicate key handling) across
      all repositories

  Weak:
    - The cache framework has 15+ classes for what is fundamentally
      "get from Redis, deserialize, handle miss/tombstone/negative."
      The VersionCodec/ValueCodec/CacheEncoder/CacheDecoder/
      VersionCacheEncoder hierarchy has more interfaces than
      implementations. For a project with exactly two cache strategies,
      this is over-abstracted
    - The ReadRedisSupport -> SimpleRedisSupport / VersionedRedisSupport
      inheritance tree adds a layer that provides little value. The
      shared get() method in ReadRedisSupport could be a utility method
      or part of the concrete classes

  Improvement:
    Collapse the codec layer. VersionCodec and ValueCodec could be a
    single class with a "versioned" boolean flag, or two static
    methods. The interface separation (CacheEncoder, CacheDecoder,
    VersionCacheEncoder) serves no purpose when each has exactly one
    implementation.

================================================================================
 MODULE 2: ledger-service
================================================================================

1. PROBLEM DECOMPOSITION                                              8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The layering is clear and intentional: gRPC service -> processor
      -> store (cache+DB orchestration) -> repository -> mapper.
      Each layer has a defined role and doesn't leak into adjacent layers
    - LedgerTxnStore as a separate "store" layer that orchestrates
      cache and DB is a good decomposition. It isolates the caching
      strategy from both the business logic (processors) and the raw
      data access (repositories). Processors don't know about cache;
      repositories don't know about cache. Clean
    - The separation of PostLedgerProcessor (write path) and
      GetLedgerTxnProcessor (read path) reflects the read/write
      asymmetry in the domain

  Weak:
    - The Kafka consumer (DefaultListener) contains business routing
      logic (switch on event_type) mixed with infrastructure concerns
      (ACK, outbox insert, error handling). A dispatcher/handler
      pattern would make the event routing extensible without modifying
      the listener

  Improvement:
    Extract event dispatching from DefaultListener into a registry
    pattern: Map<String, EventHandler> where each handler processes
    one event type. The listener becomes a pure infrastructure
    component that deserializes, dispatches, and handles ACK/error.


2. DOMAIN MODELING                                                    8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The core domain is modeled correctly: LedgerTxn (transaction
      header) + LedgerEntry (individual debit/credit lines) +
      Account (balance holder) + Asset (instrument definition).
      This is standard double-entry bookkeeping
    - The double-entry invariant (sum of debits == sum of credits per
      asset) is validated before persistence, which is the correct
      place — it's a pre-condition, not a post-condition
    - The referenceId on LedgerTxn allows callers to correlate their
      business transactions with ledger records. This is a necessary
      abstraction for a multi-service system
    - Amount as long (minor units) avoids floating-point precision
      issues — correct for financial data

  Weak:
    - Account has no balance field. The ledger is an event-sourced
      design (balances derived from entries), but there's no mechanism
      to query account balance. This is fine if the wallet owns
      balance tracking (which it does), but it means the ledger
      cannot independently verify that a debit doesn't overdraw an
      account. The ledger trusts callers completely — the balance
      invariant is caller-side, not ledger-side
    - LedgerEntry has no sequence number or position field. The TODO
      at LedgerEntry.java line 19 acknowledges this: "should we add
      a seq field...so that a txn cannot insert entries once it has
      been posted." The current design allows entries to be appended
      to an already-posted transaction (though the code doesn't do
      this, the schema doesn't prevent it)

  Improvement:
    Add a (txn_id, seq) composite unique key on ledger_entries. This
    makes the "entries are immutable once posted" invariant structural
    rather than convention-based. The seq can be the position in the
    request's entry list.


3. ARCHITECTURE QUALITY                                               8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - Dual ingress (gRPC sync + Kafka async) with the same processor
      (PostLedgerProcessor) is a clean architecture. The processor
      doesn't know or care whether it was invoked synchronously or
      asynchronously — the business logic is ingress-agnostic
    - The two-level cache design (refId -> txnId -> LedgerTxn) with
      different strategies per level (stable vs versioned) shows
      genuine thought about the data characteristics at each level
    - Kafka reply via outbox (not direct Kafka produce) ensures the
      reply is persisted before the consumer ACK. This prevents the
      "processed but reply lost" failure mode

  Weak:
    - The ledger service has no balance tracking. It records entries
      but cannot answer "what is account X's balance?" This is a
      deliberate delegation to the wallet, but it means the ledger
      cannot enforce credit limits, overdraft protection, or any
      balance-based business rule. The ledger is a pure append-only
      journal. This is architecturally valid but limits the ledger's
      role to a passive recorder rather than an active participant

  Improvement:
    This is a design choice, not necessarily a flaw. But if the system
    evolves to need ledger-side balance enforcement (e.g. regulatory
    requirements for real-time balance verification), the ledger would
    need a materialized balance view. Designing the entry insertion
    to optionally update a materialized balance (via DB trigger or
    application logic) would future-proof the architecture.


4. CORRECTNESS BY DESIGN                                              8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The double-entry balance check is enforced at the request
      validation level (reqPrecheck), not deferred to DB constraints.
      This means imbalanced transactions are rejected before touching
      storage — fail-fast design
    - INSERT IGNORE on ledger_transactions.reference_id provides a
      DB-level uniqueness guarantee as the final backstop behind
      the Redis idempotency. The design doesn't trust any single
      layer — defense in depth
    - The idempotency flow has a clear ownership model: claim with
      token -> process -> mark done with token -> on error, release
      only if you own the token (Lua CAS). The ownership model
      prevents most cross-request interference

  Weak:
    - The reqPrecheck validates entry balance but does NOT validate
      that entries reference distinct accounts. Two entries debiting
      and crediting the same account would pass validation (balanced)
      but be economically meaningless. The design relies on callers
      to not do this

  Improvement:
    Add a structural check: reject transactions where any account
    appears on both sides (debit and credit) in the same transaction,
    or at minimum log a warning. Self-transfers are usually a sign
    of a bug in the caller.


5. CONSISTENCY AND CONCURRENCY DESIGN                                 8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The versioned cache-aside with Lua CAS is a textbook solution
      to the cache invalidation problem. The tombstone-after-write
      pattern (write DB -> set tombstone with new version) correctly
      handles the race between concurrent reads and writes
    - The @Version optimistic lock on LedgerTxn ties the DB version
      directly to the cache version, creating a single source of
      truth for ordering
    - The idempotency claim uses SET NX (atomic) and release uses
      Lua compare-and-delete (atomic). Both critical operations are
      single-step at the Redis level

  Weak:
    - The negative cache write is unguarded (plain SET), creating a
      window where a slow reader can overwrite a writer's positive
      value with a stale negative. The versioned cache path doesn't
      have this problem because the Lua CAS prevents stale writes

  Improvement:
    Already covered in common-util evaluation. Use SET NX for negative
    cache, or better: have the post-insert cleanup write the positive
    value (refId -> txnId) instead of just deleting the negative.
    This way, the cache transitions directly from negative to positive
    without a gap.


6. RELIABILITY AND RECOVERY DESIGN                                    8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The three-tier idempotency with self-healing (DB fallback
      re-populates Redis) means the system recovers from Redis
      failures without manual intervention
    - Cache errors trigger self-recovery (delete corrupted entries)
      and never block the main flow. This is a principled design
      decision applied consistently
    - The outbox pattern with SKIP LOCKED provides reliable async
      delivery even across service restarts. No messages are lost
      if the process crashes after DB commit

  Weak:
    - There's no explicit monitoring or alerting surface. The system
      self-recovers from many failure modes, but operators have no
      visibility into HOW OFTEN recovery is happening. Frequent
      self-recovery could indicate a systemic issue (e.g. Redis
      instability) that needs human attention

  Improvement:
    Instrument the self-recovery paths with metrics counters.
    "Self-healing" is excellent for availability but needs
    observability to prevent silent degradation.


7. SCALABILITY AND PERFORMANCE THINKING                               6/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The two-level cache (ref -> txnId -> txn) avoids redundant
      data in Redis. The refId cache stores just a string (txnId),
      not the full object. This is memory-efficient
    - Cursor-based pagination in LedgerEntryRepository (keyset
      pagination via lastId) is the correct approach for large
      result sets

  Weak:
    - No account caching (treated as fixed, see assumptions), but more
      fundamentally: the batch INSERT for ledger_entries is a single
      SQL statement for all entries in a transaction. For transactions
      with many entries, this could hit MySQL's max_allowed_packet
      or produce very large redo log entries
    - No read-path caching for entries. If getTxnById with
      includeEntries=true is called frequently for the same txn,
      every call re-fetches entries from DB. Entries are immutable
      once posted — an obvious caching candidate that was overlooked

  Improvement:
    Add entry caching keyed on txnId. Entries are immutable after
    the transaction is posted, making them ideal for aggressive
    caching with long TTLs and no invalidation logic needed.


8. SIMPLICITY VS OVER-ENGINEERING                                     7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The processor layer is genuinely simple. PostLedgerProcessor
      is one method with a clear flow: validate -> claim -> resolve
      -> persist -> finalize. No unnecessary abstractions
    - Using Murmur3-128 for request hashing is pragmatic — fast,
      well-distributed, no need for cryptographic strength here.
      Simple and correct
    - The gRPC service classes are thin dispatchers with try/catch.
      No framework magic, no interceptors, no middleware chain.
      Easy to read and debug

  Weak:
    - The LedgerTxnStore comment at line 34-37 openly admits: "using
      a version CAS cache here is like overkill...I'm testing version
      CAS cache in the ledger txn query." The versioned cache is more
      complex than needed for mostly-immutable data. The honest comment
      is appreciated, but it's still over-engineering for the current
      use case (ledger txn metadata is rarely updated)

  Improvement:
    For the ledger's current needs, StableCacheAbstract (the simpler
    strategy) would suffice for LedgerTxnCache, with a plain DELETE
    on the rare metadata update. Reserve the versioned CAS strategy
    for data with genuine write contention. The author seems to know
    this — the comment suggests it's a learning exercise, which is
    fine in a personal project but would be flagged in production review.

 MODULE 3: wallet-service
================================================================================

1. PROBLEM DECOMPOSITION                                              8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The step-processor pattern (IdempPrecheck -> BeforePostLedger ->
      AfterPostLedger) cleanly separates the transaction lifecycle into
      distinct phases. Each step has a focused responsibility
    - The three entry-point processors (Atomic, Reserve, Apply) all
      converge into the same step processors with different parameters.
      This is the right decomposition — the variation is in the
      operation types, not in the processing logic
    - RequestInfo and TransactionInfo as explicit models for passing
      data between steps is better than passing a dozen parameters.
      These are effective "context objects" for the processing pipeline

  Weak:
    - BeforePostLedgerProcessor is doing too much: loading snapshots,
      loading reservations, creating actions, validating, creating
      outbox, running the DB transaction, marking idempotency done,
      AND publishing to Kafka. It's a 330-line class that is both
      the orchestrator and the implementor. The step-processor idea
      is good, but BeforePostLedger should be further decomposed
      into smaller steps

  Improvement:
    Split BeforePostLedgerProcessor into: LoadDataStep (fetch snapshots
    + reservations), BuildActionsStep (create actions + reservations
    from lines), ValidateStep, PersistStep (DB transaction), and
    PublishStep (Kafka). The orchestrator becomes a pipeline of
    composable steps. This also makes each step independently testable.


2. DOMAIN MODELING                                                    9/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The two-bucket balance model (available + reserved) correctly
      captures the real-world concept of "funds you can spend" vs
      "funds held for pending operations." This is the right
      abstraction for an exchange wallet
    - The reservation model with its five-field lifecycle
      (total, remaining, consumed, pendingSettle, released) and the
      invariant total == remaining + consumed + pendingSettle + released
      is a thorough model. It captures every possible state of a
      held amount, including the intermediate "pending settle" state
      during async ledger posting
    - The OperationTypePb -> ActionType expansion is a key design
      insight. A single high-level operation (e.g. Debit) maps to
      multiple low-level actions (Reserve + Consume + TransferOut).
      This allows the system to track each bucket movement
      independently while presenting a simple API to callers
    - The reservation outcome inference (CONSUMED, RELEASED, PARTIAL)
      based on the final distribution of amounts is a clean piece
      of domain logic. It derives state from data rather than
      tracking it explicitly
    - WalletTransaction's idempotencyKey is separate from referenceId.
      This is a deliberate and correct modeling choice — the same
      business reference might need to be retried with a new
      idempotency key, or different references might share an
      idempotency namespace

  Weak:
    - There is no explicit "balance" type. The balance is implicitly
      two longs (available, reserved) on the BalanceSnapshot entity.
      A Balance value object would make the dual-bucket invariant
      (available >= 0, reserved >= 0, no operation makes either
      negative) more explicit in the type system

  Improvement:
    This is a minor modeling improvement. The SQL-level guards
    (WHERE available >= amount) already enforce non-negativity.
    A Balance value object would add compile-time documentation
    but the runtime correctness is already there.


3. ARCHITECTURE QUALITY                                               8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The async choreography between wallet and ledger via Kafka
      (command/reply pattern over outbox) is architecturally sound.
      Neither service blocks waiting for the other. The wallet
      optimistically updates its own state (reserve funds, create
      txn as PENDING) and asynchronously reconciles when the ledger
      confirms
    - Wallet owns balances, ledger owns the audit trail. This is the
      right split. The wallet is the "hot" path (balance checks,
      reservations), while the ledger is the "cold" path (immutable
      records). Each is optimized for its access pattern
    - The wallet-to-ledger mapping via WalletAccountMapping allows
      the two services to use their own internal IDs while maintaining
      a mapping table for correlation. If the mapping ever becomes
      M:N (e.g. sub-accounts), the architecture supports it

  Weak:
    - The wallet creates the PostTransactionRequestPb directly in
      ObjectBuilder, embedding knowledge of the ledger's API contract
      deep in the business logic. If the ledger API evolves, changes
      propagate into the wallet's processor internals. An
      anti-corruption layer or dedicated mapper at the service
      boundary would be cleaner
    - There is no reconciliation mechanism between wallet balances
      and ledger entries. If they diverge (e.g. due to a bug in
      AfterPostLedger), there's no way to detect or repair the
      discrepancy. For a financial system, this is an architectural
      gap

  Improvement:
    Design a reconciliation process that periodically computes
    expected wallet balances from ledger entries and compares
    them with balance_snapshots. This is a standard pattern in
    financial systems and is the safety net that catches bugs in
    the real-time processing path.


4. CORRECTNESS BY DESIGN                                              8/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - Balance updates use SQL-level atomic guards:
      UPDATE ... SET available = available - N WHERE available >= N
      This is the strongest possible guarantee against negative
      balances — it's enforced by the database, not by application
      logic. Even with bugs in the application, the balance cannot
      go negative. This is correctness by design
    - The reservation locking (SELECT FOR UPDATE + optimistic lock
      on all amount fields) is defense-in-depth. The pessimistic
      lock prevents concurrent access, and the optimistic lock
      catches logic bugs. This is over-cautious in a good way
    - The balance validation (sum of TRANSFER_IN == sum of
      TRANSFER_OUT per asset) mirrors the ledger's double-entry
      check at the wallet level. The invariant is enforced at both
      the initiator and the recorder — belt and suspenders across
      service boundaries

  Weak:
    - The operation type validation for reserve transactions is
      partial: ReserveTransactionProcessor validates all lines are
      OperationTypePb_Reserve (line 62), but ApplyReservation does
      NOT validate that lines are Earmark or Release. Invalid
      operation types would be caught by the switch-case in
      createActionsFromLine (ObjectBuilder line 103: throws
      InvalidEnumException), but this is a runtime exception rather
      than a graceful validation error

  Improvement:
    Add explicit operation type validation in each processor before
    reaching ObjectBuilder. Each transaction type should declare its
    allowed operation types, and the validation should reject
    disallowed types with a clear error message.


5. CONSISTENCY AND CONCURRENCY DESIGN                                 7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The snapshot update ordering (sorted by id) within a single
      DB transaction prevents self-deadlock. Combined with the
      SQL-level guards (WHERE available >= amount), this provides
      correct serialization for concurrent transactions on the
      same wallet
    - The two-phase transaction design (reserve first, apply later)
      is fundamentally a saga pattern. Reservations act as
      compensatable transactions — the RELEASE action is the
      compensation. This is the correct pattern for distributed
      financial workflows
    - The idempotency key being caller-provided (not system-generated)
      gives callers control over retry semantics. Combined with the
      hash check, this prevents both duplicate processing and
      request mutation

  Weak:
    - The snapshot updates and reservation updates are in the SAME
      DB transaction, which means the lock duration includes both.
      For transactions touching many wallets, this could hold row
      locks for a long time, increasing contention and deadlock risk
    - The AfterPostLedger phase re-reads all data from DB (actions,
      snapshots, reservations) rather than receiving it from the
      Kafka message payload. This is safer (DB is source of truth)
      but means the completion path does 3-4 DB queries before the
      actual update transaction

  Improvement:
    Consider splitting the snapshot update and reservation update
    into separate DB transactions within BeforePostLedger. Update
    snapshots first (the hot contention point), commit, then
    update reservations and insert records in a second transaction.
    This reduces the lock duration on the hot snapshot rows.
    The tradeoff is more complex recovery logic if the second
    transaction fails, but the reservation state can be reconciled.

    Assumption: this may not be feasible without redesigning the
    atomicity guarantees. The current single-transaction approach
    is simpler and correct, just slower under contention.


6. RELIABILITY AND RECOVERY DESIGN                                    6/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - Wallet creation has crash recovery: INIT state allows resumption
      from any point in the multi-step creation flow
    - The outbox pattern ensures ledger posting commands survive
      process crashes
    - AfterPostLedger is idempotent (hasFinalized check) so Kafka
      redelivery is safe

  Weak:
    - No reconciliation cron for PENDING transactions (treated as
      fixed per assumptions, but the design doesn't include it)
    - No recovery for INIT wallets (treated as fixed per assumptions)
    - The Kafka consumer's error handling is simplistic — ALL failures
      are RetriableException. There's no circuit breaker, no DLQ
      routing, and the TODO at line 59 indicates the author knows
      this is incomplete
    - PostServiceClient exists but is unused. The gRPC direct-call
      path to ledger is available but not used for reconciliation
      or fallback. This is an underutilized capability

  Improvement:
    The biggest reliability gap is the lack of a reconciliation loop.
    Add a scheduled job that queries PENDING transactions older than
    a threshold, checks their status in the ledger (via gRPC
    getTxnByRefId), and either completes or rolls them back.
    This is the standard "saga coordinator" pattern.


7. SCALABILITY AND PERFORMANCE THINKING                               5/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The balance_snapshot design puts all balance data in a single
      row per wallet, making balance reads O(1) rather than requiring
      aggregation over entries. This is the right materialization for
      a hot read path

  Weak:
    - No caching anywhere in the wallet service. Every request hits
      DB for snapshots, reservations, and mappings. The ledger has
      a sophisticated cache framework; the wallet uses none of it.
      This is surprising given that the wallet is the higher-TPS
      service (user-facing)
    - WalletAccountMapping is queried on every ledger-posting
      transaction but is immutable after creation. Not caching it
      is a missed opportunity (treated as fixed per assumptions)
    - BalanceSnapshot is queried by walletReferenceId IN (...), but
      the wallet service doesn't batch these across transactions.
      Under high concurrency, the same snapshot row is read
      repeatedly by different concurrent transactions
    - The gRPC call to ledger AccountService during wallet creation
      has no timeout, no retry policy, and no circuit breaker. A
      slow ledger blocks wallet creation unboundedly

  Improvement:
    Add Redis caching for BalanceSnapshot (read path) with short TTL
    and invalidation on write. The cache should be per-walletId and
    invalidated by the same transaction that updates the snapshot.
    This requires careful design (the snapshot is mutable), but
    the StableCacheAbstract from common-util is not suitable here —
    a VersionCacheAsideAbstract with the snapshot's version would be
    appropriate.

    Alternatively, accept that wallet balances are DB-bound and focus
    on optimizing the DB path (connection pooling, read replicas for
    non-transactional reads). The SQL-level atomic guards already
    require hitting the DB for writes; adding a cache only helps reads.


8. SIMPLICITY VS OVER-ENGINEERING                                     7/10
────────────────────────────────────────────────────────────────────────────

  Strong:
    - The operation-type-to-action-list expansion (ObjectBuilder.
      createActionsFromLine) is an elegant piece of design. Instead
      of having separate code paths for atomic vs two-step, the
      system normalizes everything into actions. The complexity is
      in the mapping, not in the processing
    - The reservation lifecycle is complex but necessarily so — it
      models a real-world financial workflow (hold, partial consume,
      partial release). The five-field model is not over-engineered;
      it's domain-accurate
    - The ValidateHelper.validateAssetInfo doing a wallet-level
      double-entry check (TRANSFER_IN == TRANSFER_OUT per asset)
      is simple validation that catches a class of bugs early

  Weak:
    - The TransactionInfo model has a walletIdToPostActions map
      that filters for "post" actions (TRANSFER_IN/OUT/CONSUME) at
      construction time. This is a derived view that should arguably
      be computed on demand rather than pre-materialized in a model
      object. It creates coupling between the model and the processing
      steps that consume it
    - Having three nearly-identical entry-point processors (Atomic,
      Reserve, Apply) that each build a RequestInfo and call the same
      two steps is repetitive. A single parameterized processor with
      a strategy enum would be simpler

  Improvement:
    Unify the three entry-point processors into a single
    TransactionProcessor with a method per RPC that builds the
    appropriate RequestInfo and calls the shared pipeline. The
    current three classes have nearly identical structure (idemp
    check -> beforePostLedger -> build reply). The variation is
    in RequestInfo construction and reply building, which can be
    parameterized.

 CLOSING ANALYSIS

1. STRONGEST DESIGN DECISIONS
────────────────────────────────────────────────────────────────────────────

  a) SQL-level atomic guards for balance updates
     UPDATE ... SET available = available - N WHERE available >= N
     This is the single best design decision in the project. It makes
     negative balances structurally impossible regardless of application
     bugs. It's the right level of abstraction for the invariant — the
     database enforces it, not the application.

  b) Three-tier idempotency (Redis -> DB unique key -> DB fallback)
     Each tier compensates for the failure modes of the tier above.
     Redis key expiry? DB catches the dup. DB down? Redis fast-path
     still works. Redis AND DB both have stale data? DB fallback
     re-populates Redis. This is defense-in-depth applied correctly.

  c) The reservation lifecycle model (total/remaining/consumed/
     pendingSettle/released)
     This accurately models the real-world financial concept of
     "held funds in various stages of settlement." The invariant
     (total == sum of all fields) is elegant and auditable. The
     derived outcome (CONSUMED/RELEASED/PARTIAL) is a clean piece
     of domain logic.

  d) Separation of wallet (balances) from ledger (audit trail)
     The wallet owns the hot path (balance checks, reservations).
     The ledger owns the cold path (immutable records). Each is
     optimized for its access pattern. Neither blocks the other
     (async via Kafka outbox). This is sound microservice decomposition.

  e) Cache error tolerance as a design principle
     Every cache read in the system follows: try cache -> on error,
     log + self-recover + fall through to DB. This is applied
     consistently, not ad-hoc. It means a complete Redis failure
     degrades to "slower, not broken" — exactly the right behavior.


2. WEAKEST DESIGN DECISIONS
────────────────────────────────────────────────────────────────────────────

  a) No reconciliation mechanism between wallet and ledger
     This is the most significant gap. In any financial system, the
     primary control is reconciliation — periodically verifying that
     two independent records agree. The wallet has balances, the
     ledger has entries, and there's no process to verify they match.
     A bug in AfterPostLedger could cause permanent divergence with
     no detection.

  b) No caching in the wallet service
     The wallet is the user-facing, high-TPS service, yet it has no
     caching layer. Every request hits DB for snapshots, mappings,
     and reservations. The ledger service (lower TPS, internal) has
     a sophisticated cache framework. The priority is inverted.

  c) Over-abstracted cache framework in common-util
     15+ classes for two cache strategies is too many layers. The
     inheritance hierarchy (ReadRedisSupport -> SimpleRedisSupport
     / VersionedRedisSupport -> SimpleCacheClient / VersionCacheClient
     -> StableCacheAbstract / VersionCacheAsideAbstract) has more
     indirection than value for the current scale. The framework is
     correct but harder to understand than it needs to be.

  d) Ledger has no balance enforcement
     The ledger accepts any balanced transaction without checking
     whether the source account has sufficient funds. It relies
     entirely on the wallet to enforce this. If a bug in the wallet
     allows an overdraft, the ledger will happily record it. This
     is a design choice (the ledger is a "dumb journal") but it
     means the system has no independent verification layer.


3. SIGNS OF MATURE ENGINEERING JUDGMENT
────────────────────────────────────────────────────────────────────────────

  a) Defense-in-depth applied consistently. The idempotency system
     has three tiers. The balance system has SQL guards + validation.
     The reservation system has pessimistic + optimistic locking.
     The cache system has self-recovery. This pattern of "never
     trust a single mechanism" shows experience with production systems.

  b) The idempotency key release is guarded (Lua compare-and-delete),
     not just a blind DELETE. This shows awareness of the specific
     failure mode where a different request could have claimed the
     key after TTL expiry.

  c) The outbox pattern is used for all Kafka publishing, not just
     sometimes. There's no direct Kafka.send() from business logic
     — it always goes through the outbox. This consistency shows
     discipline in applying patterns.

  d) The honest TODO comments ("this is overkill", "redesign the
     error logic", "add hash check here") show self-awareness about
     shortcuts and incomplete areas. Production codebases where
     engineers pretend everything is finished are harder to improve.

  e) Amount as long (minor units) throughout the entire system, with
     no conversions or floating-point anywhere. This is a decision
     that prevents an entire class of financial bugs.


4. SIGNS OF OVER-DESIGN OR UNNECESSARY COMPLEXITY
────────────────────────────────────────────────────────────────────────────

  a) The cache framework's class hierarchy. 15+ classes for what could
     be 4-5 well-designed classes. The separate interfaces for
     CacheEncoder, CacheDecoder, VersionCacheEncoder each have one
     implementation — the interfaces provide no value.

  b) Versioned CAS cache for mostly-immutable LedgerTxn data. The
     author acknowledges this ("overkill...tech drill"). A simpler
     stable cache with DELETE-on-update would suffice.

  c) The EnumMapper bidirectional mapping is elegant but creates
     static HashMap instances with double-brace initialization
     (anonymous inner classes). A simpler approach would be two
     EnumMap instances or a builder pattern.

  d) The BaseEntity with autofill handler adds a layer of implicit
     behavior (auto-setting created_at/updated_at) that could be
     done with DB defaults or MyBatis-Plus's built-in auto-fill.
     The custom handler adds indirection without clear benefit.


5. THE 3 HIGHEST-LEVERAGE DESIGN IMPROVEMENTS
────────────────────────────────────────────────────────────────────────────

  1. ADD A RECONCILIATION PROCESS

     Impact: Closes the biggest correctness gap in the entire system.
     Design: A scheduled job that computes expected wallet balances
     from ledger entries (via gRPC getTxnByRefId or a dedicated
     reconciliation API) and compares with balance_snapshots.
     Discrepancies are logged and optionally auto-corrected or
     alerted. This is standard practice in every production financial
     system and is the #1 missing piece.

  2. ADD CACHING TO THE WALLET SERVICE

     Impact: Addresses the primary scalability bottleneck.
     Design: Cache WalletAccountMapping (immutable, StableCacheAbstract),
     and BalanceSnapshot (mutable, short TTL or VersionCacheAside).
     The mapping cache is trivial. The snapshot cache requires careful
     invalidation (invalidate within the same transaction that updates
     the snapshot, using tombstone + version). The common-util cache
     framework already supports this; the wallet just needs to use it.

  3. ADD EXPLICIT TERMINAL STATES AND MONITORING FOR ASYNC FLOWS

     Impact: Closes the reliability gap for async transaction completion.
     Design: Add FAILED/TIMED_OUT states to WalletTransaction. Add a
     reconciliation cron that detects stuck PENDING transactions and
     either completes or fails them. Add metrics for: PENDING age,
     idemp conflicts, balance guard rejections, outbox retries.
     This transforms the system from "self-healing but opaque" to
     "self-healing and observable."
