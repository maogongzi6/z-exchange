# ID Design Implementation Doc


## Scope

This doc defines the ID scheme for internal entities such as wallet transactions, wallet actions, and ledger transactions.

## Goals

1. fast MySQL/InnoDB storage and indexing
2. globally unique machine identity
3. direct stateless lookup from a single reference token
4. stable routing across shard evolution
5. one uniform internal reference across DB, logs, API, and messaging

## Final model

Default for core business entities:

1. `internal_id`: global machine identity, `BIGINT UNSIGNED`, primary key
2. `*_ref`: internal resolvable reference token, `VARCHAR`, unique
3. `external_id`: optional public/business-facing reference, `VARCHAR`, unique when needed

Examples:

1. `wallet_txn_ref`
2. `wallet_action_ref`
3. `ledger_txn_ref`

Optional:

1. a separate `id BIGINT AUTO_INCREMENT` may still be used on some tables if you intentionally want storage PK decoupled from global identity

## Responsibilities

### `internal_id`

1. canonical machine identity
2. generated by distributed ID generator
3. default primary key for core business tables
4. used for search, decode, reconciliation, and owner-table lookup

### `*_ref`

1. canonical internal reference token
2. used in logs, messaging, APIs, and relational references when lookup needs routing information
3. decodes to routing metadata plus `internal_id`

## `*_ref` format

Recommended structure:

`<TYPE>-<V>-<B>-<P>-<ENC_INTERNAL_ID>-<CHK>`

Fields:

1. `TYPE`: entity code, for example `WTX`, `WACT`, `LTX`
2. `V`: route/format version
3. `B`: virtual bucket number
4. `P`: business partition when routing depends on business time or other business partition
5. `ENC_INTERNAL_ID`: encoded `internal_id`, base32/base62
6. `CHK`: checksum

Notes:

1. `P` is required only when routing depends on business partition
2. `B` is logical routing information, not physical shard number
3. do not include `env`
4. do not include physical DB/table number

## Routing model

Physical table resolution must use:

1. `route_version`
2. `virtual_bucket`
3. optional `business_partition`
4. routing configuration

Rule:

`*_ref` carries logical location data.  
Routing config maps logical location to physical DB/table.

## Storage rules

### Owner table

Each owner table stores:

1. `internal_id`
2. `*_ref`
3. optional `external_id`

Example:

```sql
CREATE TABLE wallet_action (
    internal_id BIGINT UNSIGNED NOT NULL PRIMARY KEY,
    wallet_action_ref VARCHAR(64) NOT NULL,
    ...
    UNIQUE KEY uk_wallet_action_ref (wallet_action_ref)
);
```

### Referencing table

Default rule for this system:

1. if a table references another entity and later lookup needs routing data, store `*_ref`
2. do not require callers to pass bucket or partition separately

Example:

```sql
CREATE TABLE action_relation (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    wallet_action_ref VARCHAR(64) NOT NULL,
    ...
    KEY idx_wallet_action_ref (wallet_action_ref)
);
```

Optional optimization later:

1. add derived decoded columns
2. add generated columns
3. add extra indexes

These are optimization choices, not the base contract.

## Reference rules

1. cross-service stored reference: store `*_ref`
2. same-system relational reference: store `*_ref` when direct lookup requires routing info
3. owner service search: search by `internal_id` or `*_ref`
4. public/external business flows: use separate external business ID, not `*_ref`

## Generator rules

`internal_id` generator must provide:

1. global uniqueness
2. high availability without hot-path SPOF
3. approximate time order only

Operational requirements:

1. worker identity allocation must be unique
2. clock rollback policy must be defined
3. sequence overflow policy must be defined
4. generator versioning must be reserved

## Prohibitions

1. do not use `id` outside owner table boundaries
2. do not encode environment into `*_ref`
3. do not encode physical shard/table into `*_ref`
4. do not parse `*_ref` for unrelated business logic branching
5. do not expose `*_ref` as public business-facing ID

## Implementation checklist

1. define `internal_id` generator bit layout and ops policy
2. define `*_ref` format and checksum
3. define route-version and virtual-bucket mapping config
4. implement shared encode/decode library
5. add DB unique indexes for `internal_id` and `*_ref`
6. standardize logging fields
7. standardize API/message field names

## Standard names

Use:

1. `internal_id`
2. `wallet_txn_ref`
3. `wallet_action_ref`
4. `ledger_txn_ref`

Avoid ambiguous names like:

1. `txn_id` for a string token
2. `ref_id` when the entity-specific name is available

## Four ID layers

Use four distinct ID layers with clear scope:

1. `internal_id`: canonical internal machine identity
2. `*_ref`: canonical internal locator/reference token
3. `external_id`: customer/partner/support-facing business reference
4. optional `id`: local DB primary key only when a table intentionally keeps storage identity separate from `internal_id`

### `internal_id`

Use for:

1. internal unique identity
2. owner-table search
3. reconciliation
4. decode/search tooling
5. default PK for core business tables

Do not use for:

1. external display
2. routing when routing cannot be derived from it alone

### `*_ref`

Use for:

1. internal APIs
2. messaging
3. logs
4. same-system references when lookup needs routing information
5. cross-service stored references

Do not use for:

1. public/customer-facing display
2. physical topology encoding

### `external_id`

Use for:

1. UI display
2. partner-facing APIs
3. customer support
4. receipts, statements, emails, screenshots

Requirements:

1. stable
2. readable
3. copyable
4. should not leak internal routing or topology
5. should not depend on `*_ref` format

Note:

1. not every entity needs an `external_id`
2. only entities that humans or external systems must reference should have one

### optional `id`

Use only when:

1. you intentionally want clustered storage key decoupled from global identity
2. you want maximum flexibility to change global ID format later
3. a specific table benefits from strict auto-increment clustering

Do not use for:

1. cross-service references
2. external display

## PK choice: `AUTO_INCREMENT` vs `internal_id`

### `AUTO_INCREMENT BIGINT` as PK

Good:

1. strict append-like clustering
2. best insert locality in InnoDB
3. strongest decoupling between storage PK and global identity

Costs:

1. requires one extra column
2. requires one extra unique index for `internal_id`
3. more schema and semantic complexity

Use when:

1. the table is extremely insert-hot
2. you want storage identity independent from global identity design
3. you want easier future migration if global ID format changes

### `internal_id BIGINT` as PK

Good:

1. simpler schema
2. one fewer index
3. same `BIGINT` comparison cost as auto-increment PK
4. secondary indexes remain compact because PK is still 8 bytes
5. Snowflake-like IDs still keep inserts concentrated in the hot tail instead of scattering across the full B-tree like random UUIDs

Costs:

1. with multiple workers, inserts may hit several recent leaf pages instead of only the single rightmost page used by strict auto-increment
2. clustered PK is now coupled to global ID design
3. changing global ID format later is harder

Use when:

1. `internal_id` is intended to be permanent
2. generator design is mature
3. simpler schema is more valuable than maximum append-only clustering

### Default recommendation

For core business entities in this system:

1. use `internal_id BIGINT` as PK
2. keep `*_ref` as unique internal locator/reference token
3. add `external_id` only for entities that need public/business-facing reference
4. keep separate `id` only as an intentional exception, not the default

### Practical note on page split, fragmentation, and locality

1. The effect is real, but it is usually a second-order effect when the comparison is `AUTO_INCREMENT BIGINT` versus Snowflake-like `BIGINT`. It is much smaller than the gap between append-like numeric keys and random UUID/string keys.
2. IDs from different workers in the same time window are separated in key space, but they usually still land in the hot tail of the clustered index, not across the entire B-tree. Whether they truly hit very different pages depends on row size, insert rate per table, worker count, and out-of-order arrival.
3. On SSD/NVMe, physical disk seek fragmentation matters much less than on spinning disks. The remaining costs are mostly extra page splits, slightly worse page fill, more hot dirty pages in the buffer pool, and somewhat weaker cache locality.
4. In many OLTP business tables, these costs are often smaller than the cost of one extra column, one extra unique index, and the added semantic complexity of keeping both `id` and `internal_id`.
5. Strict auto-increment still wins on pure clustered insert locality, especially for a very hot single table. But that advantage usually becomes important only when one table is an obvious insert hotspot.
6. Point lookup by `internal_id` is actually cleaner when `internal_id` is the PK, because it avoids an extra unique-index lookup and avoids indirection through a separate clustered PK.
7. Batch ID allocation from one worker can improve locality only if rows are inserted roughly in generated order and within a short time window. It is a useful optimization, not a guaranteed property.
8. Default judgment for this system: keep `internal_id` as PK for core business entities unless benchmark evidence on the hottest tables shows a meaningful regression versus `AUTO_INCREMENT`.

## Decision summary

1. `internal_id` is the canonical identity and default PK
2. `*_ref` is the canonical locator/reference token
3. same-system tables may store `*_ref` for simpler semantics when routing requires it
4. `external_id` is optional and only for public/business-facing use
5. physical routing is derived from logical routing info plus routing config
6. separate auto-increment `id` is an exception used only when storage/global-ID decoupling is explicitly needed
