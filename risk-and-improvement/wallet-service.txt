================================================================================
 WALLET SERVICE — RISKS & SUGGESTED IMPROVEMENTS
================================================================================


1. RACE CONDITIONS
================================================================================

1.1 [HIGH] Balance Snapshot Updates Not Ordered Across Transactions
──────────────────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 263-289

  The snapshot updates are ordered by id WITHIN a single transaction:
    List<BalanceSnapshot> snapshotInOrder = snapshots.stream()
        .sorted(Comparator.comparing(BalanceSnapshot::getId)).collect(...);

  However, two concurrent transactions affecting the same wallets
  acquire snapshot locks in the order determined by each transaction's
  line list, NOT by a globally consistent order.

  The snapshot update uses per-row UPDATE with WHERE clauses (not
  SELECT FOR UPDATE). MyBatis-Plus UPDATE acquires row-level locks
  implicitly. If transaction A updates wallet X then wallet Y, and
  transaction B updates wallet Y then wallet X, this can deadlock.

  The sorting by id (line 264) mitigates this IF both transactions
  load the same snapshots. But the snapshots are loaded by walletRef
  (line 79), and different transactions may load different subsets.

  Contrast with UpdateReservationProcessor which explicitly uses
  SELECT FOR UPDATE with PK order (line 31) — the snapshot path
  does NOT use this pattern.

  Severity: HIGH — deadlocks under concurrent transfers between the
  same pair of wallets. Database will detect and roll back one txn,
  but the caller gets an opaque error rather than a clear retry signal.

1.2 [MEDIUM] AfterPostLedger Not Idempotent for Partial Completion
──────────────────────────────────────────────────────────────────

  File: AfterPostLedgerProcessor.java lines 50-93

  The idempotency check is:
    if (txnInfo.walletTxn.hasFinalized()) {
        return Results.success(txnInfo.walletTxn);
    }

  If AfterPostLedger crashes DURING the DB transaction (after some
  snapshot updates but before COMMIT), the transaction rolls back.
  On retry, hasFinalized() returns false (status still PENDING),
  so it re-processes everything. This is correct.

  BUT: if the crash happens AFTER COMMIT but BEFORE ack.acknowledge()
  (DefaultListener.java line 37), Kafka redelivers the message.
  AfterPostLedger runs again on a COMPLETED txn and returns early.
  This is also correct.

  The actual risk is: what if the DB transaction commits partially?
  This cannot happen (Spring transaction is atomic). So this is safe.

  Severity: LOW — the design is correct, but the lack of explicit
  documentation makes it fragile for future maintainers.

1.3 [MEDIUM] Reservation FOR UPDATE Without Consistent Ordering Across Txns
────────────────────────────────────────────────────────────────────────────

  File: UpdateReservationProcessor.java line 31

    var reservationFromDb = walletReservationManager.selectInIdForUpdate(modifyReservationIds);

  The IDs are passed as a list from the caller. The actual SQL is:
    SELECT * FROM wallet_reservations WHERE id IN (...) FOR UPDATE

  MySQL acquires row locks in the order the storage engine encounters
  them, which for InnoDB with a PK scan is PK order. So the IN clause
  with PK effectively locks in PK order. This is safe.

  However, if two concurrent transactions each lock different subsets
  of reservations that partially overlap, the FOR UPDATE on overlapping
  rows will serialize them (one waits for the other to commit). This is
  correct behavior but can cause increased latency under high contention
  on the same reservation.

  Severity: LOW — correct but potentially slow under contention.

1.4 [LOW] markIdempDone Without Ownership Check (Same as Ledger)
────────────────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 157-158

    idempRedisClient.markIdempDone(GlobalServiceId.WALLET.code, Constant.SCOPE,
        requestInfo.idempotenceKey, ..., requestInfo.token, walletTxn.getTxnId(),
        idempConfig.getDoneTtl());

  Same issue as ledger-service: markIdempDone uses unconditional SET
  (IdempRedisClient.java line 58: baseRedisSupport.set(k, v, ttl)).
  No token ownership check. If the PENDING key expired and another
  request claimed it, this overwrites their claim.

  Assessment: Same as ledger — no data corruption because DB is the
  backstop. The final ACCEPTED state is correct.

1.5 [LOW] TransactionTemplate Propagation Mutation (Same as Ledger)
───────────────────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java line 193
  File: AfterPostLedgerProcessor.java line 65
  File: CreateWalletProcessor.java line 120

  All use DbTransactionHelper.executeWithResult(template, PROPAGATION_REQUIRED, ...)

  Currently safe because all callers use PROPAGATION_REQUIRED.


2. DATA INCONSISTENCY
================================================================================

2.1 [HIGH] Wallet Stuck in INIT on Ledger Account Creation Failure
──────────────────────────────────────────────────────────────────

  File: CreateWalletProcessor.java lines 68-71

    result = createAccount(walletInDb);
    if (!result.success) {
       return replyError(result);
    }

  If the gRPC call to ledger AccountService fails (network timeout,
  ledger down, etc.), the wallet stays in INIT state. The next call
  to createWallet with the same referenceId will see the wallet in
  INIT and retry from step 4 (createAccount).

  However: if the gRPC call succeeded but the response was lost
  (network partition), the wallet is still INIT, and the next retry
  will call createAccount again. The ledger side handles this with
  insertIgnore, so no duplicate account is created.

  The real risk: if the ledger service is persistently down, the
  wallet is stuck in INIT indefinitely. There is no cron job or
  background process to retry INIT wallets. The caller must retry
  the createWallet RPC themselves.

  Severity: HIGH for operational concern — INIT wallets accumulate
  during ledger outages. No automatic recovery mechanism.

2.2 [HIGH] AfterPostLedger Failure Leaves Txn in PENDING Forever
────────────────────────────────────────────────────────────────

  File: DefaultListener.java lines 55-63

    Result<WalletTransaction> result = afterPostLedgerProcessor.afterPostLedger(reply.getReferenceId());
    if (result.isFailed()) {
        throw new RetriableException(...);
    }

  If AfterPostLedger consistently fails (e.g. snapshot not found,
  reservation mismatch, DB constraint violation), the Kafka message
  will be retried until max retries, then... what?

  The TODO at line 59 says "retry base on error" — suggesting error
  classification (retriable vs non-retriable) is not yet implemented.

  If the message is eventually dropped or DLQ'd:
    - wallet_transaction stays in PENDING forever
    - balance_snapshots have reserved funds that are never released
    - The ledger has the double-entry posted, but the wallet never
      finalized — balance mismatch between wallet and ledger
    - User sees "reserved" funds they can't use

  Severity: HIGH — financial inconsistency. Reserved funds become
  permanently locked. The ledger thinks the transfer happened, but
  the wallet never credited the recipient.

2.3 [MEDIUM] No Hash Verification in DB Fallback Check
───────────────────────────────────────────────────────

  File: IdempPrecheckProcessor.java lines 117-121

    private WalletTransaction idempDbCheck(ServiceIdPb serviceIdPb, String idempotencyKey) {
        // TODO add hash check here
        ServiceId serviceId = EnumPbMappers.serviceIdPbMapper.to(serviceIdPb);
        return walletTransactionManager.selectByIdempotencyKey(serviceId, idempotencyKey);
    }

  The TODO acknowledges the gap. When the Redis key expires and the
  DB fallback finds an existing txn, it returns success WITHOUT
  verifying the request hash. This means:

    Request A (hash=X) creates txn with idempKey="K1"
    Redis key expires
    Request B (hash=Y, different body) sends idempKey="K1"
    Redis miss -> DB finds txn -> returns txnId without hash check

  Request B gets a success response even though its body differs
  from the original request. The Redis path correctly rejects hash
  mismatches (line 109), but the DB fallback does not.

  The ledger-service has the same structural issue (PostLedgerProcessor
  line 135 queries by referenceId without hash check), but there the
  referenceId IS the natural key, while here the idempotencyKey is
  a caller-provided opaque string.

  Severity: MEDIUM — caller could unknowingly get a "success" for a
  request with different parameters.

2.4 [MEDIUM] Outbox INSERT Failure During Transaction
─────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 224-230

    if (outboxManager.insertWithClaim(outbox, ...) == 0) {
        return Results.fail(ErrorCode.WALLET_OUTBOX_DUPLICATED, ...);
    }

  The outbox insert is inside the DB transaction. If it fails
  (duplicate eventId), the entire transaction rolls back — including
  the snapshot updates, reservation updates, and txn insert.

  This is actually correct behavior (atomicity). But the error message
  "unexpected outbox duplicated" is misleading — it implies a bug,
  but it could happen if the same txnId was somehow generated twice
  (IdGenerator collision) or if there's a partial replay scenario.

  The eventId is generated as: IdGenerator.generateEventId(txn.getTxnId())
  If txnId is unique (ULID), eventId should be unique. So this
  should never happen in practice.

  Severity: LOW — theoretically sound, but the error handling treats
  it as unexpected rather than handling it gracefully.

2.5 [LOW] Reservation pendingSettle Guard in AfterPostLedger
────────────────────────────────────────────────────────────

  File: AfterPostLedgerProcessor.java lines 162-167

    if (Objects.requireNonNull(action.getActionType()) == ActionType.CONSUME) {
        if (reservation.getPendingSettle() < action.getAmount()) {
            // TODO maybe throw exception? this is severe error (overspend risk in reservation)
            return Results.fail(ErrorCode.WALLET_RESERVATION_NOT_SATISFIED, ...);
        }

  The TODO acknowledges this is a severe error — it means the ledger
  confirmed a transfer but the wallet doesn't have enough pendingSettle
  to cover it. This indicates a data integrity issue.

  Currently returns a Result.fail which will cause the DB transaction
  to roll back and the Kafka message to be retried. But if the data
  is genuinely inconsistent, retries will never succeed.

  Severity: LOW in normal operation (should never happen if
  BeforePostLedger is correct), but the TODO suggests the author
  is uncertain about the right recovery strategy.


3. SCALABILITY BOTTLENECKS
================================================================================

3.1 [HIGH] Hot Wallet Contention on balance_snapshots
─────────────────────────────────────────────────────

  File: BalanceSnapshotRepository.java (reserve/release/transferOut/In)

  Every transaction touching a wallet must UPDATE the same
  balance_snapshot row. For a hot wallet (e.g. the exchange's
  operational wallet), this row becomes a contention point.

  The UPDATE with WHERE available >= amount acquires an exclusive
  row lock. Concurrent transactions on the same wallet serialize
  at this point. Under high TPS, this creates a bottleneck.

  Unlike ledger-service (which just records entries), the wallet
  must maintain a running balance, which inherently serializes.

3.2 [MEDIUM] Synchronous gRPC Call During Wallet Creation
─────────────────────────────────────────────────────────

  File: CreateWalletProcessor.java line 111

    CreateAccountReplyPb reply = accountServiceClient.createAccount(req);

  Synchronous blocking gRPC call to ledger-service. If ledger is slow
  or has high latency, every createWallet call is blocked.

  No timeout configuration visible in the code (relies on default
  gRPC deadline, which may be unbounded).

3.3 [MEDIUM] Snapshot and Reservation Queries Not Batched Efficiently
─────────────────────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 76-95

  For each transaction:
    1. SELECT balance_snapshots WHERE wallet_reference_id IN (...)
    2. SELECT wallet_reservations WHERE reference_id IN (...)
    3. SELECT wallet_account_mappings WHERE wallet_id IN (...)
       (inside createOutboxIfNeeded, line 301)

  Three separate DB queries before the transaction even starts.
  For high-TPS scenarios, these could be combined or cached.

  Accounts are queried via walletAccountMappingManager.selectInWalletIds
  every time a ledger-posting transaction is created. Since the
  mapping is 1:1 and immutable, this is a strong caching candidate
  (same issue as ledger-service's account resolution).

3.4 [LOW] Synchronous Kafka Publish With 3s Timeout
────────────────────────────────────────────────────

  File: DefaultPublisher.java line 30

    kafkaTemplate.send(...).get(3, TimeUnit.SECONDS);

  Same issue as ledger-service. Blocks the thread during best-effort
  publish. Outbox cron handles failures, so this could be async.

3.5 [LOW] Single-Threaded Outbox Cron
─────────────────────────────────────

  File: OutboxDispatcher.java — identical pattern to ledger-service.
  Sequential claim + sequential publish. Same bottleneck.


4. SUGGESTED IMPROVEMENTS
================================================================================

4.1 [P0] Fix Deadlock Risk in Snapshot Updates
──────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 263-289
  File: AfterPostLedgerProcessor.java lines 135-159

  Current: snapshots sorted by id, then updated with individual UPDATEs.
  But the row locks are acquired implicitly by UPDATE, and two concurrent
  txns touching the same wallets in different line-list order can deadlock.

  Fix: Use SELECT FOR UPDATE before the UPDATE loop, same as
  UpdateReservationProcessor does for reservations:

    // Before the update loop:
    List<Long> snapshotIds = snapshotInOrder.stream()
        .map(BalanceSnapshot::getId)
        .collect(Collectors.toList());
    balanceSnapshotManager.selectInIdForUpdate(snapshotIds);  // lock in PK order

    // Then proceed with the per-row UPDATEs as before.

  This ensures all snapshot locks are acquired in PK order upfront,
  eliminating deadlock risk.

  Add to BalanceSnapshotRepository:
    public List<BalanceSnapshot> selectInIdForUpdate(List<Long> ids) {
        var wrapper = queryLambdaWrapper().in(BalanceSnapshot::getId, ids)
            .orderByAsc(BalanceSnapshot::getId)
            .last("for update");
        return mapper.selectList(wrapper);
    }

4.2 [P0] Add Recovery Mechanism for PENDING Transactions
────────────────────────────────────────────────────────

  Risk: If AfterPostLedger fails permanently, transactions stay PENDING
  with reserved funds locked forever.

  Option A — Cron-based reconciliation:
    @Scheduled job that:
      1. Queries wallet_transactions WHERE status=PENDING
         AND updated_at < (now - threshold)
      2. For each stale txn: queries ledger by refId
         (PostServiceClient.getTxnByRefId exists but is unused)
      3. If ledger has the txn posted: re-run AfterPostLedger
      4. If ledger does not have it: check outbox status
         - SENT: ledger lost the message -> re-publish
         - PENDING: outbox cron hasn't retried yet -> wait

  Option B — Add state machine with explicit FAILED status:
    After N retries in AfterPostLedger, mark txn as FAILED.
    A separate reconciliation process handles FAILED txns.

  Recommendation: Option A is more robust. It doesn't require new
  states and handles both "ledger processed but reply lost" and
  "ledger never received the message" scenarios.

4.3 [P0] Add Recovery Mechanism for INIT Wallets
─────────────────────────────────────────────────

  Risk: Wallets stuck in INIT during ledger outages.

  Add a cron job:
    @Scheduled job that:
      1. Queries wallets WHERE wallet_status = INIT
         AND created_at < (now - threshold)
      2. For each: retry createAccount gRPC call
      3. On success: run enableWallet DB transaction
      4. On failure: log, increment retry counter, try next cycle

  This provides automatic recovery without requiring callers to retry.

4.4 [P1] Add Hash Check to DB Fallback Idempotency
───────────────────────────────────────────────────

  File: IdempPrecheckProcessor.java lines 117-121

  The TODO already acknowledges this. Implementation:

    private WalletTransaction idempDbCheck(ServiceIdPb serviceIdPb,
            String idempotencyKey, String expectedHash) {
        ServiceId serviceId = EnumPbMappers.serviceIdPbMapper.to(serviceIdPb);
        WalletTransaction txn = walletTransactionManager
            .selectByIdempotencyKey(serviceId, idempotencyKey);

        // or recompute from stored request data

  Full fix requires storing the request hash in wallet_transactions
  (add a column). Then the DB fallback can verify the hash before
  returning success.

4.5 [P1] Cache WalletAccountMapping Lookups
───────────────────────────────────────────

  File: BeforePostLedgerProcessor.java line 301

  The wallet-to-account mapping is 1:1 and immutable (set during
  wallet creation, never changed). Every ledger-posting transaction
  queries it from DB.

  Add a simple Redis cache (same StableCacheAbstract pattern as
  ledger's LedgerRefCache):

    @Component
    public class WalletAccountCache extends StableCacheAbstract<String> {
        // key: "wallet:account:{walletId}" -> value: accountRefId
    }

  Populate on first access, never invalidate (immutable data).

4.6 [P1] Add Explicit Error Classification in Kafka Consumer
────────────────────────────────────────────────────────────

  File: DefaultListener.java lines 55-63

  Current: ALL AfterPostLedger failures throw RetriableException.

  Some errors are deterministic and should NOT be retried:
    - BALANCE_SNAPSHOT_NOT_FOUND (data integrity issue)
    - WALLET_RESERVATION_MISMATCH (data integrity issue)
    - WALLET_TRANSACTION_NOT_FOUND (impossible if ledger ref is correct)

  Fix:
    Result<WalletTransaction> result = afterPostLedgerProcessor
        .afterPostLedger(reply.getReferenceId());
    if (result.isFailed()) {
        ErrorCode code = Results.getErrorCode(result);
        if (isDataIntegrityError(code)) {
            // Route to DLQ + alert
            throw new AbnormalProtoDataException(code,
                "data integrity error, needs manual investigation: " + result);
        } else {
            // Transient — retry
            throw new RetriableException(code,
                "transient error, will retry: " + result);
        }
    }

4.9 [P3] Make Kafka Publish Async in Best-Effort Path
─────────────────────────────────────────────────────

  File: BeforePostLedgerProcessor.java lines 317-332

  The postLedger() method is already best-effort (failure doesn't
  block the main flow). Make the publish async:

    private void postLedger(Outbox outbox) {
        kafkaTemplate.send(outbox.getDestination(), outbox.getPartitionKey(), bytes)
            .addCallback(
                result -> {
                    outboxManager.updateStatusToFinalize(outbox, OutboxStatus.SENT, ...);
                },
                ex -> {
                    log.error("post ledger publish failed, outbox: {}", outbox, ex);
                });
    }

  This frees the gRPC response thread immediately after the DB commit.

4.10 [P3] Add PostServiceClient Usage for Reconciliation
────────────────────────────────────────────────────────

  File: PostServiceClient.java

  This client exists but is NOT used in any transaction flow. The
  main flow uses Kafka outbox. However, it would be valuable for
  the reconciliation cron (improvement 4.2):

    // In reconciliation cron:
    Result<PostTransactionReplyPb> result = postServiceClient
        .postTransaction(req);  // or getTxnByRefId

  The PostServiceClient already wraps the error handling. The gRPC
  getTxnByRefId RPC (defined in post_service.proto) can check if
  the ledger has a posted txn for a given wallet txnId.
