1. RACE CONDITIONS
================================================================================

1.1 [MEDIUM] Negative Cache Race After Insert
──────────────────────────────────────────────

  Files:
    LedgerTxnStore.java lines 73-84 (getByRefId, setNegative)
    PostLedgerProcessor.java line 100 (cleanNegativeCacheAfterInsert)
    StableCacheAbstract.java lines 50-57 (setNegative uses plain SET)

  Scenario:
    T0  Reader: getByRefId("REF-1") -> DB miss -> returns null
    T1  Writer: INSERT ledger_transactions (REF-1) -> success
    T2  Writer: cleanNegativeCacheAfterInsert("REF-1") -> DELETE key
    T3  Reader: setNegative("REF-1") executes AFTER the writer's clean
        (Reader was slow; its setNegative from line 76 runs after T2)
    T4  Next reader: getByRefId("REF-1") -> NEGATIVE HIT -> returns null!
        But the data EXISTS in DB.

  Root cause: StableCacheAbstract.setNegative uses SimpleCacheClient.setNegative
  which is a plain SET (SimpleRedisSupport.java line 35: "conflict risk without
  version check" — the comment acknowledges this). There is no condition to
  prevent overwriting a value that was set between the reader's DB miss and
  its cache write.

  Impact: Silently incorrect query results for the duration of negativeTtl.
  In a financial system, an upstream service may believe a transaction doesn't
  exist when it does.

  Duration of inconsistency: bounded by negativeTtl (configured in
  CustomCacheConfig.Data.negativeTtl), but still a correctness gap.

1.2 [LOW] Idempotency Key TTL Expiry Mid-Flight
────────────────────────────────────────────────

  File: PostLedgerProcessor.java lines 57-106

  Scenario:
    T0   A: SET NX idemp key -> success (PENDING, tokenA, TTL=pendingTtl)
    T1   A: starts slow processing (e.g. account resolution under DB load)
    Tttl Redis: key expires
    T+1  B: SET NX idemp key -> success (PENDING, tokenB)
    T+2  A: INSERT IGNORE -> affected=1 (first to DB)
    T+3  B: INSERT IGNORE -> affected=0 (dup) -> rollback -> release idemp

  Assessment: DB INSERT IGNORE is the backstop. No data corruption.
  B does wasted work (account lookup, entry construction, DB round-trip)
  but fails safely. The code explicitly acknowledges this design at
  PostLedgerProcessor.java line 160: "we have db idemp as the backstop".

  Condition: only triggered when actual processing time > pendingTtl.
  CustomCacheConfig.Idemp.pendingTtl comment (line 21): "this ttl should be
  long enough to cover business flow". Proper tuning prevents this.

1.3 [LOW] markIdempDone Overwrites Another Request's PENDING Claim
──────────────────────────────────────────────────────────────────

  File: IdempRedisClient.java line 56-59 (markIdempDone uses unconditional SET)

  Scenario (extends 1.2):
    After A's key expires and B claims a new PENDING key:
    A completes DB write -> markIdempDone() -> unconditional SET
    This overwrites B's "P:hash:tokenB" with "A:hash:tokenA:txnId"

  The final state is correct (ACCEPTED with the real txnId). B still fails
  safely at DB layer. But the unconditional SET is an asymmetry with the
  guarded release path (releaseIdempIfOwned uses Lua compare-and-delete).

  The release path (release-idemp-if-owned.lua) correctly checks ownership:
    if v == ARGV[1] then DEL end
  But markIdempDone (BaseRedisSupport.set) does not check ownership.

1.4 [MEDIUM] TransactionTemplate Shared Instance — Propagation Mutation
───────────────────────────────────────────────────────────────────────

  File: DbTransactionHelper.java line 12

    public static <T> T executeWithResult(TransactionTemplate template,
        int propagation, Supplier<T> supplier) {
      template.setPropagationBehavior(propagation);  // MUTATES SHARED BEAN
      return template.execute(...)
    }

  TransactionTemplate is a Spring singleton. setPropagationBehavior mutates
  its internal state. Under concurrent calls with different propagation values,
  one thread's setting can be overwritten before execute() runs.

  Currently safe: all callers pass PROPAGATION_REQUIRED (PostLedgerProcessor
  line 83, OutboxRetryHandler line 41). But this is a latent bug — any future
  caller passing a different propagation creates a concurrency issue.

1.5 [NEGLIGIBLE] Redundant Redis SET on Concurrent Stable Cache Writes
──────────────────────────────────────────────────────────────────────

  File: LedgerTxnStore.doGetByRefId lines 115-116

  If two concurrent readers both miss cache and both query DB, both will
  SET the same refId->txnId. Harmless because the mapping is immutable
  (same value), but performs redundant Redis writes.

2.2 [HIGH] Inverted Error Code Check in DefaultListener
────────────────────────────────────────────────────────

  File: DefaultListener.java lines 79-86

    if (reply.getError().getCode() != ErrorCodePb.ERROR_OK) {
        if (reply.getError().getCode() != ErrorCodePb.ERROR_INTERNAL) {
            // ^^^ INVERTED — this matches INVALID_ARGUMENT, NOT_FOUND, etc.
            throw new RetriableException(...);  // RETRIES deterministic errors!
        } else {
            throw new AbnormalProtoDataException(...);  // DLQs transient errors!
        }
    }

  The condition `!= ERROR_INTERNAL` means:
    - ERROR_INVALID_ARGUMENT, ERROR_NOT_FOUND, ERROR_ALREADY_EXISTS
      -> RetriableException (will be retried forever, can never succeed)
    - ERROR_INTERNAL (actual transient failure)
      -> AbnormalProtoDataException (goes to DLQ, never retried)

  This is backwards. Evidence: the log messages are also swapped:
    Line 80: "internal error, wait for retry" — but the condition catches
    non-internal errors
    Line 83: "non retriable, queue dlq" — but the condition catches internal errors

  Impact: Deterministic failures (bad input, missing accounts) will be
  retried indefinitely, wasting resources. Genuine transient errors get
  routed to DLQ immediately instead of being retried.

4.2 [P0] Handle Outbox Duplicate on Kafka Redelivery
─────────────────────────────────────────────────────

  File: DefaultListener.java lines 46-49

  Current:
    if (outboxManager.insertWithClaim(replyOutbox, ...) != 1) {
        throw new RetriableException(LEDGER_OUTBOX_DUPLICATED, ...);
    }

  Fix:
    int affected = outboxManager.insertWithClaim(replyOutbox, ...);
    if (affected == 0) {
        // Outbox already exists — this is a Kafka redelivery after a crash.
        // The outbox row is already persisted; cron will handle delivery.
        // Just ACK and move on.
        log.warn("outbox already exists (redelivery), commandId={}",
            replyOutbox.getCommandId());
        ack.acknowledge();
        return;

  Rationale: The outbox row existing means the business operation already
  completed successfully. The consumer should ACK to advance the offset.
  The outbox cron guarantees the reply will be delivered.

  Assumption: This assumes that if the outbox row exists, the business
  operation completed successfully. This is true because insertWithClaim
  is called AFTER handleMessage (which calls postLedgerProcessor), so the
  outbox row is only created on successful processing.

4.3 [P1] Guard Negative Cache Write With SET NX
────────────────────────────────────────────────

  File: StableCacheAbstract.java line 50 (setNegative)
  File: SimpleRedisSupport.java line 35 (plain SET)

  Current: setNegative uses unconditional SET.

  Option A — Use SET NX:
    In SimpleCacheClient:
      public Result<Void> setNegativeIfAbsent(String key, TtlStrategy ttl) {
          String encoded = cacheEncoder.encode("", CacheType.NEGATIVE);
          baseRedisSupport.setIfAbsent(key, encoded, ttl.afterJitter());
          return Results.success();
      }
    This prevents a slow reader's negative write from overwriting a value
    that was populated between the reader's DB miss and its cache write.

  Option B — Use versioned negative cache:
    Switch LedgerRefCache to use VersionCacheAsideAbstract instead of
    StableCacheAbstract. Use a monotonic counter (e.g. based on
    current timestamp) as the version. The Lua CAS script would then
    prevent stale writes. This is more robust but adds complexity to
    what is currently a simple immutable mapping.

  Recommendation: Option A. SET NX is simple and addresses the race
  without changing the architecture. The remaining edge case (writer
  deletes negative, then slow reader does SET NX which succeeds because
  key is gone, then writer sets positive value — but SET NX fails because
  negative key now exists) is actually prevented because SET NX will not
  overwrite the positive value. Wait — the writer calls cleanNegative
  (DELETE) BEFORE setting the positive value in the ref cache? Actually,
  looking at the flow:
    - PostLedgerProcessor calls cleanNegativeCacheAfterInsert (line 100)
    - But does NOT call LedgerRefCache.set() — that only happens on READ
    So the sequence is:
      Writer: DELETE negative key
      Slow reader: SET NX negative -> succeeds (key was deleted)
    With SET NX, this still races. The negative key is set after deletion.

  Revised recommendation: The clean DELETE should be changed to a
  SET of the actual positive value instead of just a DELETE:

    public Result<Void> cleanNegativeAndSetAfterInsert(String refId, String txnId) {
        return ledgerRefCache.set(refId, txnId, cacheTtlStrategies.getLedgerRefStrategy());
    }

  This way, after the writer inserts the txn:
    1. Writer sets "ledger:ref:{refId}" = "S:{txnId}" (overwrites anything)
    2. Slow reader tries setNegativeIfAbsent -> fails (key exists) -> correct

4.6 [P2] Parallelize Outbox Retry Publishing
─────────────────────────────────────────────

  File: OutboxRetryHandler.java lines 61-68

  Current: sequential publish, one-by-one, each blocking up to 3s.

  Improvement:
    // Add an ExecutorService for parallel publish
    private final ExecutorService outboxPublishExecutor =
        Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());

    // Replace sequential loop with parallel:
    List<CompletableFuture<Pair<Outbox, Boolean>>> futures = outboxes.stream()
        .map(outbox -> CompletableFuture.supplyAsync(() -> {
            Result<Void> r = publisher.publish(outbox);
            return Pair.of(outbox, r.success);
        }, outboxPublishExecutor))
        .collect(Collectors.toList());

    // Wait for all with a bounded timeout
    CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
        .get(outboxConfig.getPageTimeoutSec(), TimeUnit.SECONDS);

    for (var f : futures) {
        Pair<Outbox, Boolean> p = f.join();
        (p.getSecond() ? successOutboxes : failedOutboxes).add(p.getFirst());
    }

  This reduces worst-case latency from pageLimit * 3s to ~3s per page.

4.8 [P2] Add Idempotency Token Ownership to markIdempDone
──────────────────────────────────────────────────────────

  File: IdempRedisClient.java line 56

  Current: unconditional SET (BaseRedisSupport.set).

  Improvement — Lua script with ownership check:

    -- mark-idemp-done.lua
    local key = KEYS[1]
    local expectedToken = ARGV[1]
    local newValue = ARGV[2]
    local ttl = tonumber(ARGV[3])

    local old = redis.call('GET', key)
    if not old then
        -- Key expired, set anyway (we committed to DB, must cache result)
        redis.call('SET', key, newValue, 'PX', ttl)
        return 1
    end

    -- Verify we own the PENDING key (our token in the value)
    if string.find(old, expectedToken, 1, true) then
        redis.call('SET', key, newValue, 'PX', ttl)
        return 1
    end

    -- Someone else owns it; don't overwrite.
    -- DB is source of truth; next reader will recover via DB fallback.
    return 0

  This closes the ownership gap from risk 1.3. If another request claimed
  the key (after our key expired), we don't overwrite their PENDING state.
  The DB fallback (section 2c in the idempotency flow) ensures the correct
  result is eventually available.

4.10 [P3] Add Circuit Breaker for Redis
───────────────────────────────────────

  Currently, if Redis is down, every request pays the latency of a failed
  connection attempt before falling through to DB. Add a circuit breaker
  (e.g., Resilience4j) around BaseRedisSupport:

    When Redis is unhealthy: circuit opens -> all cache calls fail-fast
    (no network round-trip) -> DB-only throughput maintained without
    added latency.

  This matters because the cache-first pattern means EVERY request
  (postTransaction, getTxnById, getTxnByRefId) touches Redis before DB.
  A 3-second Redis connection timeout on every request would be catastrophic
  for latency.
