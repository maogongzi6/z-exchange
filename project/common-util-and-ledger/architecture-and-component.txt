================================================================================
 Z-EXCHANGE LEDGER SYSTEM — ARCHITECTURE & KEY COMPONENTS
================================================================================

1. SYSTEM OVERVIEW
================================================================================

A double-entry ledger microservice for a crypto/fintech exchange.
Records financial transactions as balanced debit/credit entries.
Exposes functionality via gRPC (sync) and Kafka (async).

Tech stack:
  - Spring Boot + grpc-spring-boot-starter (net.devh)
  - MyBatis-Plus (ORM, optimistic locking via @Version)
  - Redis (Redisson) for caching and idempotency
  - Kafka for async command/event messaging
  - Protobuf for gRPC + Kafka serialization


2. MODULE STRUCTURE
================================================================================

2.1 grpc-proto/common-proto
────────────────────────────
  Shared protobuf contracts consumed by all services in the exchange platform.

  error.proto
    - ErrorPb {code, message, detail}
    - ErrorCodePb enum: categorized error codes
      - 0: OK
      - 1-2: internal (INTERNAL, UNAVAILABLE)
      - 1000-1002: business (FAILED_PRECONDITION, CONFLICT, PROCESSING)
      - 2000-2002: validation (INVALID_ARGUMENT, UNAUTHENTICATED, UNAUTHORIZED)
      - 3000-3001: resource (NOT_FOUND, ALREADY_EXISTS)

  event_envelope.proto
    - EventEnvelopePb: standard Kafka event wrapper
      Fields: event_id, command_id, event_type (string for loose coupling),
              payload (proto bytes), occurred_at

2.2 grpc-proto/ledger-proto
────────────────────────────
  Ledger-specific gRPC service and message definitions.

  ledger_common.proto
    - Domain enums: LedgerDirectionPb (Credit/Debit), AccountCategoryPb
      (Asset/Liability), NormalSidePb, OwnerTypePb, ServiceIdPb

  account_service.proto
    - AccountService.createAccount(CreateAccountRequestPb) -> CreateAccountReplyPb
    - Request carries: reference_id, service_id, asset_id, category,
      normal_side, owner_type, owner_id

  post_service.proto
    - PostService.postTransaction(PostTransactionRequestPb) -> PostTransactionReplyPb
    - PostService.getTxnById(GetTxnByIdRequestPb) -> GetTxnReplyPb
    - PostService.getTxnByRefId(GetTxnByRefIdRequestPb) -> GetTxnReplyPb
    - LedgerEntryPb: {ledgerEntryId, accountRef, direction, amount, assetId}
    - LedgerTransactionPb: {ledgerTxnId, referenceId, extraData}

2.3 common-util
────────────────────────────
  Reusable infrastructure library. No business logic.

  Package: redis.idemp
    - IdempRedisClient: claim/release/markDone idempotency pattern
      Uses SET NX for claiming, Lua script (release-idemp-if-owned.lua)
      for atomic compare-and-delete on release
    - CommonIdempHelper: key/value format helpers
      Key format: "idemp_k:{service}:{scope}:{idempId}"
      Value format: "{status}:{hash}:{token}[:{content}]"
    - IdempValue: parsed value DTO (status, hash, token, content)
    - CommonIdempStatus: PENDING("P"), ACCEPTED("A")

  Package: redis.cache
    Hierarchy:
      BaseRedisSupport<T>          — thin wrapper over RedisTemplate
        ReadRedisSupport            — GET + decode (shared by both strategies)
          SimpleRedisSupport        — plain SET, no version (for stable data)
          VersionedRedisSupport     — Lua-based CAS SET (set-if-absent-or-newer.lua)

    Clients:
      SimpleCacheClient            — wraps SimpleRedisSupport: get/set/setNegative/delete
      VersionCacheClient           — wraps VersionedRedisSupport: get/setIfAbsentOrNewer/setTombstone/delete

    Abstract strategies (to be extended by services):
      StableCacheAbstract<T>       — for immutable data + negative caching
        Implements: StableCacheStrategy, NegativeCacheStrategy
        Operations: get, set, setNegative, cleanNegative
      VersionCacheAsideAbstract<T> — for mutable data with version-based CAS
        Implements: VersionCacheAsideStrategy
        Operations: get, setCacheAside, setTombstoneAfterWrite

    Codec layer:
      ValueCodec                   — encode/decode with type marker prefix "{S|J|T|N}:{content}"
      VersionCodec                 — wraps ValueCodec, adds version prefix "{version}|{marker}:{content}"
      CacheType enum: STRING("S"), JSON("J"), TOMBSTONE("T"), NEGATIVE("N")

    Model:
      CacheValueInfo<T>            — {value, cacheType, version}
        ifCacheHit(): true for NEGATIVE or valid value; false for null or TOMBSTONE
        getValidValue(): returns null for TOMBSTONE/NEGATIVE

  Package: outbox
    - Outbox entity: {eventType, eventId, commandId, outboxStatus, destination,
      partitionKey, payload(bytes), attemptCount, lastAttemptAt, nextAttemptAt,
      lastError, finalizedAt, metadata}
    - OutboxRepository: insertWithClaim, selectForClaimSkipLock (SELECT FOR UPDATE
      SKIP LOCKED), batchClaim, updateStatusToFinalize, batchUpdateStatusToFinalize
    - OutboxRetryHandler: cron-driven retry loop
      1. Claim page via SELECT FOR UPDATE SKIP LOCKED
      2. Batch-bump next_attempt_at
      3. Publish each claimed row
      4. Finalize successes to SENT; leave failures for next cycle

  Package: kafka
    - IPublisher: interface for publishing Outbox to Kafka
    - CustomKafkaConfig, CommandContainerRegister, StairStepBackOff,
      KafkaErrorHandlingRegister

  Package: db
    - DbBaseRepository<T, M>: wraps MyBatis-Plus BaseMapper
      Provides insertIgnore() (catches DuplicateKeyException -> returns 0)
    - DbTransactionHelper: executeWithResult() auto-rollbacks on Result.isFailed()
    - BaseEntity: common fields (created_at, updated_at via AutofillMetaObjectHandler)

  Package: utils
    - Result<T>: {success, value, errorCode(PbMappableErrorCode), errorDetail}
    - PbMappableErrorCode interface: toProto() -> ErrorCodePb, getMessage()
    - CommonErrorCode enum: SUCCESS, LUA_SCRIPT_EXECUTE_ERROR, INVALID_IDEMP_KEY,
      INVALID_IDEMP_VALUE, PARSE_CACHE_ERROR (all map to ERROR_INTERNAL)
    - Results: factory methods success()/fail()
    - TokenHelper: UUID-based token generation ("{service}-{uuid}")
    - StableHashHelper: Murmur3-128 hash for deterministic request fingerprinting
    - JitterHelper: adds random millis to Duration
    - TtlStrategy: {ttl, jitter} with afterJitter() for cache stampede prevention
    - EnumMapper: bidirectional proto <-> domain enum mapping

2.4 ledger-service
────────────────────────────
  The application service. Structured in clean layers.

  gRPC endpoints (service package):
    - AccountServiceImpl extends AccountServiceGrpc.AccountServiceImplBase
      @GrpcService, delegates to CreateAccountProcessor
    - PostServiceImpl extends PostServiceGrpc.PostServiceImplBase
      @GrpcService, delegates to PostLedgerProcessor, GetLedgerTxnProcessor

  Business processors (processor package):
    - CreateAccountProcessor
      Validates enums, checks asset exists in DB, generates accountId,
      INSERT IGNORE on accounts table (idempotent by reference_id unique key)
    - PostLedgerProcessor
      Core posting flow: idempotency gate -> validation -> account resolution
      -> DB transaction -> cache cleanup -> finalize idempotency
    - GetLedgerTxnProcessor
      Lookup by txnId or refId, delegates to LedgerTxnStore (cache-aware),
      optionally loads entries via LedgerEntryRepository

  Data store layer (dao.store):
    - LedgerTxnStore: orchestrates cache + DB for ledger transactions
      Two cache paths:
        txnId lookup: LedgerTxnCache (versioned CAS)
        refId lookup: LedgerRefCache (stable + negative) -> chains to LedgerTxnCache

  Cache layer (dao.cache):
    - LedgerTxnCache extends VersionCacheAsideAbstract<LedgerTxn>
      Key pattern: "ledger:id:{txnId}"
    - LedgerRefCache extends StableCacheAbstract<String>
      Key pattern: "ledger:ref:{refId}"

  Repository layer (dao.repository):
    - AccountRepository: getAccountIdInRef(refs) -> batch SELECT by reference_id IN
    - LedgerTxnRepository: getByTxnId, getByRefId, updateMetadataByPk (with @Version)
    - LedgerEntryRepository: getByTransactionId (cursor-based batching via lastId)

  Kafka (kafka package):
    - DefaultListener: consumes WALLET_POST topic
      Parses EventEnvelopePb -> dispatches by event_type -> calls PostLedgerProcessor
      -> writes reply Outbox -> ACKs Kafka -> tries immediate publish
    - DefaultPublisher implements IPublisher: sends Outbox as proto bytes via KafkaTemplate

  Outbox cron (cronjob.outbox):
    - OutboxDispatcher: @Scheduled, invokes OutboxRetryHandler.retry()
    - OutboxConstant: BASE_ATTEMPT_INTERVAL_MS

  Domain model (po package):
    - Account: {accountId, serviceId, referenceId, category, normalSide,
      ownerId, ownerType, assetId, accountStatus}
    - LedgerTxn extends BaseEntity: {txnId, referenceId, metadata, version}
    - LedgerEntry: {entryId, txnId, assetId, accountId, amount, direction}
    - Asset: {assetId, assetType, symbol, decimals, extraData}
    - Enums: Direction, AccountCategory, NormalSide, OwnerType, ServiceId,
      AccountStatus, AssetType, OutboxEventType

  Config (config package):
    - CustomCacheConfig.Idemp: pendingTtl, doneTtl, jitterMs
    - CustomCacheConfig.Data: indexCacheTtl, dataCacheTtl, tombstoneTtl,
      negativeTtl, jitter
    - DbQueryConfig: defaultBatchSize

  Error handling (result package):
    - ErrorCode enum implements PbMappableErrorCode: each value maps to an
      ErrorCodePb (e.g. LEDGER_NOT_FOUND -> ERROR_NOT_FOUND)
    - Results: service-level factory (casts PbMappableErrorCode to ErrorCode)
    - PbErrorBuilder: assembles ErrorPb proto from ErrorCode + detail string

  Utils (utils package):
    - EnumMappers: bidirectional mappings for all proto <-> domain enums
    - PbConverter: LedgerTxn/LedgerEntry -> protobuf conversion
    - OutboxHelper: Outbox <-> EventEnvelopePb conversion, reply construction
    - IdGenerator: ULID-based ID generation for txnId, entryId, accountId, eventId
    - EntryHelper, ValidateHelper: domain validation utilities


3. KEY COMPONENT STRUCTURE
================================================================================

3.1 PostLedgerProcessor — The Heart
────────────────────────────────────
  File: ledger-service/.../processor/post/PostLedgerProcessor.java

  Dependencies injected:
    - CustomCacheConfig.Idemp idempConfig     (TTL configuration)
    - LedgerEntryMapper ledgerEntryMapper     (direct mapper for batch insert)
    - AccountRepository accountManager        (account lookup)
    - LedgerTxnRepository ledgerTxnRepository (txn CRUD)
    - IdempRedisClient idempRedisClient       (idempotency gate)
    - TransactionTemplate transactionTemplate (programmatic tx)
    - LedgerTxnStore ledgerTxnStore           (cache cleanup)

  Methods:
    postTransaction(req) -> PostTransactionReplyPb
      Orchestrates the full posting lifecycle (see logic.txt for details)
    idempClaimAndReqValidate(req, token) -> Result<String>
      Three-tier idempotency check: Redis claim -> cache state -> DB fallback
    claimIdempCacheIfAbsent(req, token) -> Result<IdempValue>
      SET NX with hash verification on existing keys
    reqPrecheck(req) -> Result<Void>
      Double-entry balance validation per asset
    getReqStableHash(req) -> String
      Deterministic Murmur3-128 hash of sorted entries for conflict detection

3.2 LedgerTxnStore — Cache Orchestration
─────────────────────────────────────────
  File: ledger-service/.../dao/store/LedgerTxnStore.java

  Dependencies:
    - LedgerTxnRepository (DB access)
    - LedgerTxnCache (versioned CAS cache for txnId -> LedgerTxn)
    - LedgerRefCache (stable cache for refId -> txnId, with negative caching)
    - CacheTtlStrategies (TTL configuration holder)

  Methods:
    getByTxnId(txnId):
      LedgerTxnCache.get -> [miss/tombstone] -> DB -> LedgerTxnCache.setCacheAside
    getByRefId(refId):
      LedgerRefCache.get -> [negative: return null] -> [hit: chain to getByTxnId]
      -> [miss] -> DB -> populate both LedgerRefCache + LedgerTxnCache
      -> [db miss] -> setNegative on LedgerRefCache
    updateMetadataByPk(txn):
      DB update (optimistic lock) -> setTombstoneAfterWrite (invalidate cache)
    cleanNegativeCacheAfterInsert(refId):
      DELETE the negative cache key after a new txn is inserted

3.3 Idempotency System — Three-Tier Defense
────────────────────────────────────────────
  Layer 1: Redis fast-path (IdempRedisClient)
    Key: "idemp_k:LEDGER:post_ledger:{referenceId}"
    Value formats:
      PENDING: "P:{murmur3_hash}:{uuid_token}"
      ACCEPTED: "A:{murmur3_hash}:{uuid_token}:{txnId}"
    Operations:
      claimIdempIfAbsent: SET NX with pendingTtl
      markIdempDone: unconditional SET with doneTtl (overwrites PENDING -> ACCEPTED)
      releaseIdempIfOwned: Lua compare-and-delete (only owner can release)
      forceDeleteIdemp: unconditional DELETE (self-recovery for corrupted values)

  Layer 2: DB unique key (INSERT IGNORE on ledger_transactions.reference_id)
    Catches any duplicate that slips past Redis (e.g. key TTL expiry)

  Layer 3: DB fallback query
    If Redis has no key, queries DB for existing txn by reference_id
    Re-populates Redis if found (self-healing)

3.4 Cache Framework — Two Strategies
─────────────────────────────────────
  Strategy A: Versioned Cache-Aside (for mutable data)
    Used by: LedgerTxnCache
    Wire format: "{version}|{J|T}:{json_or_empty}"
    Write: Lua script atomically checks version >= existing before SET
    Invalidation: Tombstone with new version (forces next read to DB)
    Self-recovery: DELETE on parse error

  Strategy B: Stable Cache (for immutable data + negative)
    Used by: LedgerRefCache
    Wire format: "{S|N}:{content_or_empty}"
    Write: plain SET (safe because mapping never changes)
    Negative: "N:" marker with short TTL, blocks repeated DB misses
    Cleanup: DELETE after insert (clears stale negative markers)

3.5 Outbox Pattern
──────────────────
  Write path (DefaultListener):
    1. Process Kafka command -> get result
    2. Build Outbox row (PENDING, destination=reply topic)
    3. INSERT IGNORE outbox (atomic with ACK decision)
    4. ACK Kafka consumer offset
    5. Best-effort immediate publish via DefaultPublisher

  Retry path (OutboxRetryHandler via OutboxDispatcher cron):
    1. SELECT FOR UPDATE SKIP LOCKED (pending, not maxed retries, due)
    2. Batch claim by bumping next_attempt_at + attempt_count
    3. Publish each row via IPublisher
    4. Finalize successes: UPDATE status -> SENT
    5. Leave failures: will be picked up next cycle

  Delivery guarantee: at-least-once
    Outbox row persists atomically in same DB as business state.
    Consumer must be idempotent (which it is, via the three-tier gate).


4. DATA FLOW DIAGRAMS
================================================================================

4.1 Sync gRPC — Post Transaction
─────────────────────────────────
  Caller --gRPC--> PostServiceImpl
                      |
                PostLedgerProcessor
                      |
       1. Generate token (UUID)
       2. Idempotency gate (Redis -> DB fallback)
       3. Validate double-entry balance
       4. Resolve account references -> accountIds
       5. DB Transaction: INSERT txn + batch INSERT entries
       6. Clean negative cache
       7. Mark idempotency DONE
       8. Return txnId

4.2 Async Kafka — Wallet Posts Ledger
─────────────────────────────────────
  Wallet --Kafka(WALLET_POST)--> DefaultListener
                                     |
              1. Parse EventEnvelopePb
              2. Dispatch by event_type -> PostLedgerProcessor
              3. Build reply Outbox
              4. INSERT IGNORE outbox
              5. ACK Kafka
              6. Best-effort publish reply -> Kafka(REPLY_WALLET)
              7. Cron retries if publish failed

4.3 Query Transaction
─────────────────────
  Caller --gRPC--> PostServiceImpl.getTxnById / getTxnByRefId
                      |
              GetLedgerTxnProcessor
                      |
               LedgerTxnStore (two-level cache)
                      |
       For txnId: LedgerTxnCache -> [miss] -> DB -> populate cache
       For refId: LedgerRefCache -> [negative: null] -> [hit: chain txnId]
                  -> [miss] -> DB -> populate both caches / set negative
                      |
       If includeEntries: LedgerEntryRepository (cursor-based batch)

4.4 Create Account
──────────────────
  Caller --gRPC--> AccountServiceImpl
                      |
              CreateAccountProcessor
                      |
       1. Map proto enums -> domain enums
       2. Validate fields + normalSide/category rule
       3. Verify asset exists
       4. INSERT IGNORE account (idempotent by reference_id UK)
