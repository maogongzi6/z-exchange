# Ledger Write Latency Observability Update

## Scenario

The previous k6 dashboard queried:

```promql
max(k6_ledger_write_request_duration_p95{request_kind="original"})
```

The Trend was split by entry count, duplicate timing, request kind, and
outcome. `max()` returned the worst subgroup p95 rather than the percentile of
all requests, potentially overstating overall latency.

## Client Latency Change

- `ledger_write_request_duration`: every attempt, tagged only by
  `operation=postTransaction`.
- `ledger_write_success_duration`: validated new and idempotent successes,
  tagged only by the same operation.
- The primary panel compares overall and successful p95/p99 without `max()`.
- The old detailed panel remains as a legacy diagnostic for historical data.
- `LEDGER_STRESS_MAX_P95_MS` now checks overall attempt p95.

Comparing both populations prevents fast failures from lowering successful
latency while retaining the latency observed across all attempts.

## Server And Infrastructure Change

The ledger-service dashboard now compares:

- gRPC overall p95 with transport-OK p95;
- business overall p95 with successful-result p95;
- DB transaction overall p95 with committed-success p95.

The correlation section also includes JVM GC pause maximum and Hikari active,
maximum, pending, acquisition-latency, and timeout signals. These panels help
determine whether latency changes align with processing, GC, or DB pool pressure.
